# 03. Build plan

The build is packaged as work packages (WPs), each sized for one agent session, grouped in phases with explicit dependencies, acceptance criteria, and traps. Phases 0 to 5 are planned package by package. Phases 6 to 10 are planned as epics with package estimates, and each is broken into packages when the phase before it is half done, so the detail reflects what the earlier phases taught. The status table at the end is the live work queue; update it in the same pull request as the work.

## Progress

Phases 0 and 1 are done, and Phase 2 is under way: the packages marked `in progress` or `review` in the status table at the end are the open work, and the first alpha is tagged when Phase 2's exit demo (M2) passes. The status table is the live work queue.

## How an agent uses this plan

1. Read `README.md`, `AGENTS.md`, [the roadmap](01-roadmap.md), [the architecture](02-architecture.md), and [the clean-room policy](https://github.com/loombridge/beatlayer/blob/main/CONTRIBUTING.md#building-without-abletons-code).
2. Take the first package in the status table whose status is `todo` and whose dependencies are `done`. Set it to `in progress` with the date in a first commit on branch `wp/<id>-<slug>`.
3. If the package reproduces Live behaviour, write or update its behaviour spec in `docs/specs/` first, citing only allowed sources.
4. Build to the acceptance criteria. Every criterion is a test or a command whose result is pasted into the pull request.
5. Run `cargo xtask check` (format, clippy with warnings denied, tests, the licence and advisory check, the real-time safety tests). It must pass.
6. Update the status table (status `review`, the date, the PR link) and any document whose facts changed.
7. Open the pull request to `main`. Name the package, list the acceptance evidence, and state any deviation from the design with its reason. The orchestrating agent merges it when the local check and CI pass, the review finds no blocker, and the acceptance evidence is complete.

Sizes: **S** is under two hours, **M** is half a day, **L** is a day. If a package grows past L, split the rest into a follow-up package rather than stretching the session.

Rules that never bend during the build:

- Clean room. No Ableton code, content, or trademarks, by any route ([policy](https://github.com/loombridge/beatlayer/blob/main/CONTRIBUTING.md#building-without-abletons-code)).
- The real-time rules in [the architecture](02-architecture.md#real-time-rules). No allocation, lock, or blocking call on an audio thread, ever, including "only in this rare case".
- Engine, model, and device crates never depend on a UI crate.
- The UI's placement, menus, and shortcuts follow [the UI parity reference](ui-parity/README.md) (D16). A deliberate difference needs a design rule.
- Every user-facing action is a registered command with a schema, a description, and a permission class, reachable through the agent API, with a test that drives it there (D17).
- Every feature has a headless test path through `bl-cli` or a unit test. A feature that can only be tested by clicking isn't done.
- No new dependency whose licence `cargo deny` rejects. No dependency that downloads code at build time. Spikes under `spikes/`, the fuzzing harness under `fuzz/`, and the RealtimeSanitizer harness under `rtsan/` are tools and evidence, not product: they sit outside the workspace, never ship, and are exempt from `deny.toml`, and none of their dependencies enters the workspace without passing it.
- No plug-in binaries, Ableton files, or third-party sample content in the repo. Test audio is generated by scripts in `tests/fixtures/gen/`.
- No `git add -A`. No edit to a merged migration or a golden reference without the reason in the PR.

## Phase 0: Foundations

Goal: a workspace that builds, tests, and packages on all three platforms; sound out of every platform; the core types; the UI framework chosen.

### WP-0.1 Workspace and tooling (S)

- **Depends on:** nothing.
- **Build:** the Cargo workspace with every crate in [the architecture](02-architecture.md#crates) as a stub; `rust-toolchain.toml` pinned to a stable release; workspace lints; `rustfmt.toml`; `deny.toml` that accepts only licences compatible with GPL-3.0-or-later and fails on advisories; `cargo xtask check`; `LICENSE`; `AGENTS.md`.
- **Acceptance:** `cargo xtask check` passes on macOS. A scratch crate depending on a crate with an incompatible licence makes `cargo deny check` fail (paste the output).
- **Traps:** don't publish crates to crates.io.

### WP-0.2 CI on three platforms (M)

- **Depends on:** WP-0.1.
- **Build:** GitHub Actions running `cargo xtask check` on macOS arm64, Windows x64, and Ubuntu x64, with dependency caching and the Linux audio and X11 development packages. A nightly workflow builds release binaries.
- **Acceptance:** a green run on all three. A pull request with a deliberate clippy warning fails (link the run).
- **Traps:** use `macos-15` (arm64) runners. Don't let any build script download an SDK: `cpal`'s `asio` feature fetches Steinberg's SDK when `CPAL_ASIO_DIR` is unset, which is why ASIO goes through `azo` (D9).

### WP-0.3 Audio out on all three platforms (M)

- **Depends on:** WP-0.1.
- **Build:** the `bl-audio-io` trait and its first backend. `bl-cli devices` lists devices with their sample rates and buffer sizes. `bl-cli tone` plays a 440 Hz sine on a chosen device, rate, and buffer size, and counts dropouts.
- **Acceptance:** `bl-cli tone --seconds 300 --buffer 128` on a Mac reports zero dropouts (paste the log). The Windows (WASAPI and ASIO) and Linux (PipeWire, JACK, ALSA) backends build in CI and run against a null device.
- **Traps:** the default device can change mid-stream on macOS. WASAPI may not honour the requested buffer size; report the actual size. On many Linux systems "ALSA" is PipeWire's ALSA plug-in.

### WP-0.4 Real-time thread harness (M)

- **Depends on:** WP-0.3.
- **Build:** real-time priority per platform (macOS audio workgroup join through Beatlayer's own `os_workgroup` bindings, Windows MMCSS "Pro Audio", Linux rtkit with a `SCHED_FIFO` fallback); denormal flushing; the allocation trap; a RealtimeSanitizer job in CI; a lock-free logger; an `rt_test!` helper that runs code under the trap.
- **Acceptance:** a test that allocates under the trap fails, and a test that takes a mutex fails under RealtimeSanitizer. A test shows denormals are flushed. `bl-cli tone --verbose` reports the thread's priority class and, on macOS, the workgroup it joined.

### WP-0.5 Time and tempo (M)

- **Depends on:** WP-0.1.
- **Build:** `Ticks`, `Frames`, the tempo map (constant and ramp segments), the time-signature map, bar-beat-sixteenth formatting, and conversions.
- **Acceptance:** property tests (10,000 cases) show ticks to frames to ticks within one tick. Ramp integration matches numerical integration to within 1 ns.

### WP-0.6 Document model and undo (L)

- **Depends on:** WP-0.5.
- **Build:** `bl-model` with project, tracks (audio, MIDI, group, return, main), arrangement clips, clip-data stubs, and device stubs; stable IDs; commands; transactions; undo and redo; a change set for the compiler.
- **Acceptance:** a property test applies random sequences of 1 to 200 commands, undoes them all, and gets the starting document back; redo gets the final one. Record the memory used by 10,000 undo steps on a 100-track project.

### WP-0.7 Project file, version 1 (M)

- **Depends on:** WP-0.6.
- **Build:** the project folder, zstd-compressed JSON with a schema version, the migration scaffold, backups, and atomic saves (write a temporary file, then rename). A fuzz target for the loader.
- **Acceptance:** a save and load round-trip property test. Ten minutes of fuzzing without a panic. A test that interrupts a save leaves the previous file readable.

### WP-0.8a GPUI spike (L), WP-0.8b egui spike (L), and WP-0.8c decision (S)

- **Depends on:** WP-0.1. Runs alongside the engine packages.
- **Build:** the same benchmark scene in GPUI (0.8a) and egui (0.8b): 200 tracks and 5,000 clips with waveforms from synthetic peaks, scroll and zoom, a virtualised browser list of 100,000 files, 200 animated meters, a clip drag, a knob drag with pointer lock, a rename text field, a screen-reader tree, hi-DPI, and a second native window that embeds a child native view through `raw-window-handle` (the stand-in for a plug-in editor).
- **Acceptance (per candidate):** median and 99th-percentile frame times on macOS, Windows, and Linux; idle CPU with nothing moving; VoiceOver and NVDA read the track names; pointer lock and child-view embedding work on all three platforms. WP-0.8c records the decision and updates D8. The decision also weighs how faithfully each toolkit can reproduce Live's layout (D16): placement to the pixel, dense small text, focus that moves between areas, and context-dependent and held key bindings.
- **Traps:** judge the toolkit on the shell and standard widgets, since the dense views draw through custom GPU pipelines whichever toolkit wins. Embedding a foreign child window may need the toolkit's raw event loop rather than its convenience runner.

### WP-0.9 Engine skeleton and program swap (L)

- **Depends on:** WP-0.4, WP-0.6.
- **Build:** the node trait, `EngineProgram`, a compiler from the model (main bus and tracks with a test-tone node), the swap through a lock-free queue, node migration, the drop thread, and engine state for the UI (playhead, meters) through triple buffers.
- **Acceptance:** a stress test recompiles 1,000 times during playback under the allocation trap without an allocation on the audio thread or a dropout. A counter node keeps its state across swaps.

### WP-0.10 Offline render and golden tests (M)

- **Depends on:** WP-0.7, WP-0.9.
- **Build:** `bl-cli render PROJECT OUTPUT.wav`, and a golden-test harness that renders fixtures and null-tests them against stored FLAC references.
- **Acceptance:** a fixture renders bit-identically twice. Changing one sample in the output fails the test. The same fixture nulls below −96 dBFS across the three platforms in CI.

### WP-0.11 Packaging (M)

- **Depends on:** WP-0.2.
- **Build:** `cargo xtask package` for an unsigned `.app` with its `Info.plist` and entitlements, an MSI, and an AppImage and tarball. Nightly CI uploads them.
- **Acceptance:** each artefact builds on its platform in CI, and the packaged binary starts and reports its version (`beatlayer --version`); on macOS the DMG is mounted and the app run from it. Changed on 10 October 2026, because the app has no window until WP-1.7; WP-1.7's packaged build shows the window.

### WP-0.12 Contributor docs and the clean-room gate (S)

- **Depends on:** WP-0.1.
- **Build:** `CONTRIBUTING.md` with the Developer Certificate of Origin, a pull request template with the clean-room declaration, a code of conduct, issue templates, and a behaviour-spec template in `docs/specs/`.
- **Acceptance:** the files exist and the PR template shows the declaration.

### WP-0.13 UI parity reference (L)

- **Depends on:** nothing.
- **Build:** `docs/ui-parity/`, the specification every UI package is checked against (D16):
  - `README.md`: how to use the reference, its sources, the Live version observed, and the method.
  - `layout.md`: every view and panel in Live 12 (Control Bar, browser, Session View, Arrangement View, Mixer sections, Clip View, Device View, Groove Pool, Info View, Learn View, Status Bar, the second window, Settings), each with its position, its size relative to its neighbours, what shows or hides it, and the controls inside it in order. Every row has an ID (such as `L-ARR-012`) that UI packages cite.
  - `shortcuts.toml`: every keyboard shortcut, by context, with its macOS and Windows bindings, whether it acts on press or while held, an ID, and the milestone that binds it. `shortcuts.md` is generated from it by `cargo xtask ui-parity`, and `cargo xtask check` fails if the two drift apart.
  - `menus.md`: every menu-bar menu, its items in order with separators and shortcuts, and the main context menus (clip, track header, device title bar, browser item, time selection, Session slot, scene).
  - `interactions.md`: mouse gestures and modifiers (drag, copy-drag, double-click, right-click), focus movement, and drop targets.
- **Acceptance:** every shortcut in the manual's keyboard-shortcut chapter is in `shortcuts.toml` with both platforms' bindings (report the count, and list any that couldn't be confirmed); every view and panel the manual names has a layout row; `menus.md` covers every menu; the generated table is in sync. Placement measured from Live running at 1600 × 1000 points.
- **Traps:** paraphrase; never copy the manual's text. Don't commit screenshots of Live: they're Ableton's artwork. Record placement as text and proportions. Windows bindings aren't always the macOS ones with Ctrl for Cmd; record each platform as the manual gives it. Note the Live version behind each row.

### WP-0.14 Command registry for people and agents (M)

- **Depends on:** WP-0.6.
- **Build:** the command registry (D16, D17): every command has an ID, a label, contexts, default bindings, an argument and result schema generated from its Rust types (`schemars`), a description written for a model, and a permission class (read, edit, destructive, external). Convert WP-0.6's commands to it. `cargo xtask commands` generates `docs/commands.md`, the command reference.
- **Acceptance:** a test fails when a command lacks a schema, a description, or a permission class (show it failing, then passing). Every WP-0.6 command is registered. The generated reference is in sync, checked by `cargo xtask check`.
