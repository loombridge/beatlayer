## The behaviour

The browser's Plug-Ins label lists the plug-ins installed on this machine as Live 12 lays them out: a folder for each vendor, in name order, and inside it each plug-in by name, once for each format it comes in, with a badge naming the format. A format is listed only while Settings ▸ Plug-Ins switches it on (Use VST3 Plug-In System Folders, Use Audio Units v2), all off in a new install as Live's are; CLAP, which Live doesn't host, has no switch and is always listed. Beatlayer scans by itself when it starts, in the background so the first frame doesn't wait, and again when one of those switches turns on; Rescan, in the same settings, looks for every plug-in afresh. Selecting a plug-in in the browser selects it; Enter, a double-click, or dropping it on a track loads it, as `plugin.load` does. A plug-in that crashed or hung while it was being scanned isn't listed but is remembered on a blocklist, with the reason, so nothing tries to load it again by accident; the set's list of plug-ins (`plugin.list`) names any the set uses that this machine doesn't have, and why. Hidden plug-ins and a preferred format change only what the browser and search show, never what a set may load.

A scan describes each plug-in by running it, so a plug-in's own code can crash or hang the process it runs in. Beatlayer therefore scans in `beatlayer-scan`, a child process with a timeout: when the child stops answering or dies, the scanner kills it (if it still runs), records the plug-in on the blocklist, and carries on with the next file. The main process never loads a plug-in's code to scan it. LV2 is the one format whose metadata is read without running the plug-in (lilv reads the bundle's Turtle files); its child process then instantiates each plug-in once, which does run its code, so an LV2 plug-in that crashes or hangs is blocklisted like the others, and the app itself only describes a bundle through lilv.

The scanner caches what it found by the plug-in file's path, size, and modification time, so a scan of files that haven't changed reads the cache and only loads the ones that did, and a plug-in removed from a folder the scan searched is forgotten. The cache and the blocklist are kept in the config directory with the rest of the app's settings. The browser lists what the cache knows from the first frame; the scan at start then adds what changed. `beatlayer-scan` ships in the app bundle beside the app's executable, where the scanner looks for it.

CLAP and VST3 are scanned, each in its format's own folders, Audio Units on macOS, and LV2 on Linux, with the same scanning, cache, blocklist, and commands: a `.lv2` bundle folder counts as one file holding its plug-ins, and its folders are the ones `LV2_PATH` names, or the standard ones when it is unset ([LV2 hosting](lv2-hosting.md)). The browser's Hide Plug-In and Show Plug-In items, its Show Hidden Plug-Ins switch and the Preferred Plug-In Format setting are [the browser's tags](browser-tags.md) R41 to R44, and the Devices, Format and Creator filter groups over the Plug-Ins label are its R7 and R19; the Function group comes with automatic tagging (milestone M9), and a plug-in's fold triangle of presets isn't drawn yet.

## Rules

- **R1.** `plugin.scan` finds the plug-in files in the paths it's given (a file, a folder searched below it, or each format's own system plug-in folders when no path is given; for VST3, the format's user, system and network folders) and describes each one: its format, file, identifier, name, vendor and version when it gives them, its role in a chain from its features, and whether it sends notes on from a note output, which lets it sit in the MIDI-effect position of a MIDI track's chain (IMP-24). (S2, S3)
- **R2.** The scanner caches each plug-in file by its path, size, and modification time; a scan of a file whose size and time are unchanged answers from the cache without loading it. A bundle folder's size and time are those of its contents (the total size of its files and the newest modification time of anything in it), so a bundle updated in place is loaded again; an LV2 bundle's are its `manifest.ttl`'s (R10). The cache is kept in the config directory and read again at the next start. (S1)
- **R3.** The scanner loads each plug-in in the `beatlayer-scan` child process, never in the main process, and waits at most a timeout for it. (S1)
- **R4.** A plug-in whose scan crashes, hangs past the timeout, or refuses to load doesn't stop the scan: the child is stopped and the plug-in is put on the blocklist with the reason the child gave, or that it crashed when it gave none. The blocklist is kept with the cache, with the file's size and modification time. A plain scan leaves a blocklisted file alone until its size or time changes, so a plug-in that hangs costs its timeout once; Rescan (R6) tries it again. A helper process a plug-in starts can't hold the scan open: on Unix the child gives the plug-in no copy of its reply pipe, and on every platform the scanner waits a bounded time for the reply after the child exits. (S1)
- **R5.** The test plug-ins (`bl-test-clap`, `bl-test-vst3` and `bl-test-lv2`) can be told to crash or to hang when they're scanned, so R3 and R4 are tested with a real plug-in of each format. Only the tests use this. (Beatlayer's own testing rule.)
- **R6.** `plugin.rescan` scans the same paths again, ignoring the cache and clearing the blocklist for them. (S1, S4)
- **R7.** The Plug-Ins label lists what the scanner found, and search over it matches by name. Hidden plug-ins are left out unless "Show hidden" is on; when a plug-in exists in more than one format, the preferred format is the one shown. Hiding a plug-in never stops a set from loading it, and it's remembered by its format and identifier, so moving its file keeps it hidden. `plugin.settings` sets the format preference back to none with `null` ([the browser's tags](browser-tags.md) R44). (S4)
- **R8.** `plugin.list` names every plug-in the set uses, grouped by format and identifier, with the devices and tracks that use it, each device's preset name ([plugin list](plugin-list.md) R5), and whether this machine has it (`missing`, with `blocked` and the reason when the scanner blocklisted its file). (S3)
- **R9.** `plugin.scan`, `plugin.rescan`, `plugin.list`, and `plugin.settings` are registered commands with schemas and descriptions, so an agent reaches them. Scanning reads files outside the project, so it's in the external permission class. (Beatlayer's command rule.)
- **R10.** CLAP and VST3 are scanned; VST3's files are found in the format's own user, system and network folders on each platform, and its loader is the VST3 host's (WP-2.7). Audio Units are scanned on macOS (WP-2.8). LV2 is scanned on Linux (WP-5.39): its files are the `.lv2` bundle folders in the folders `LV2_PATH` names (`~` is the home folder) or, when it is unset, in `~/.lv2`, `/usr/lib/lv2`, `/usr/lib64/lv2`, `/usr/local/lib/lv2` and `/usr/local/lib64/lv2`; a bundle folder counts as one file holding several plug-ins, described together; the child process reads the bundle with lilv, which runs no plug-in code, then instantiates each plug-in once to see that it loads, so one that crashes, hangs or won't instantiate is blocklisted with the reason (a bundle with several plug-ins keeps the ones that load, and is blocklisted only when none does); and the cache is kept by the bundle's `manifest.ttl` (its size and modification time), as editing a bundle in place doesn't change its folder's; the other bundle formats (VST3, CLAP and Audio Unit folders) are kept by their contents, as R2 says. The scanner's format type, the extension it searches for, and the command's format all take any format, and each format's hosting adds the loader. (S1)
- **R11.** The Plug-Ins label lists a folder per vendor, in name order and closed at first, holding each of its plug-ins by name, one row per format, with a badge naming the format; a plug-in that names no vendor follows the folders, and a search lists the matching plug-ins with their vendors. Opening a vendor's folder closes the one open before. A row's key is `plug-ins:/` and the vendor for a folder, and the plug-in's file, `#`, and its identifier for a plug-in; `browser.select`, `browser.open_folder`, `browser.load_selected` and a drag take these keys. Enter, a double-click or `browser.load_selected` loads the selected plug-in as `plugin.load` (or `plugin.load_au`) does, onto the selected track (with none selected, onto a new track: MIDI for an instrument or MIDI effect, audio for an audio effect), or in place of the device being hot-swapped; an instrument replaces the selected track's instrument; each as one undo step; dropping it on an Arrangement track loads it onto that track. A preview of a plug-in is refused, as it isn't an audio file. (S5, S6)
- **R12.** Settings ▸ Plug-Ins has Rescan Plug-Ins, which runs `plugin.rescan` in the background, and the Use Audio Units v2, Use Audio Units v3 and Use VST3 Plug-In System Folders switches, all off in a new install (`plugin.settings`). The browser lists VST3 plug-ins only while the VST3 switch is on and Audio Units only while Use Audio Units v2 is on; CLAP is always listed. Turning a switch on scans that format's system folders in the background. Use Audio Units v3 is kept, but app-extension Audio Units aren't scanned. A scan of the system folders (`plugin.scan` without paths) covers the formats switched on; a scan of named paths covers every hosted format. (S5, S6)
- **R13.** The app scans the system folders of the formats switched on when it starts, in a background thread, answering unchanged files from the cache; the browser lists the cache from the first frame and what the scan found when it ends. The scanner never holds its cache's lock while a plug-in is being described, so the browser and `plugin.list` read it during a scan. A plug-in whose file has left a folder the scan searched is forgotten. (S4, S5)
- **R14.** `beatlayer-scan` is packaged in the app, beside its executable, and signed with it, so a packaged app's scan finds the scanner. (S1)

**A plug-in's presets in the browser (WP-6.66)**

- **R15.** A plug-in's row in the Plug-Ins label (R11) has a fold triangle when the plug-in has presets (L-BRW-016). Opening it lists them under the row, by name: first the Beatlayer presets saved from that plug-in, in the User Library's folder for it ([device chains](device-chains.md) R17) and in the other places, known by the plug-in's format and identifier in each preset; then, for an Audio Unit, its preset files in the system's and the person's Audio Units preset folders, by manufacturer and plug-in, and, once the unit has been loaded on a track, the unit's own factory presets. VST3 and CLAP plug-ins list Beatlayer presets only, as Live lists no VST presets. Opening a plug-in's presets closes another plug-in's that were open, as vendors' folders do (R11). (S7, S8)
- **R16.** Save Preset on a plug-in device writes the plug-in's own saved state into the preset with its parameter values, as a rack preset holds its plug-ins' state ([racks](racks.md) R42). Loading the preset into a device of the same plug-in (its format and identifier) restores that state, as one undo step named Load Preset ([device chains](device-chains.md) R14, R16), and the device takes the preset's name ([the plug-in list](plugin-list.md) R5). A plug-in device's preset saved before has no state, and loads its parameter values only. (S8)
- **R17.** Enter, a double-click or a drag of a plug-in's preset loads the plug-in with that preset, onto the selected track, a new track or the track dropped on, as R11 loads a plug-in, as one undo step. While a device of the same plug-in is armed for hot-swap, the preset loads into it in place; while a device of another kind but the same role is armed, the plug-in with the preset replaces it, as [racks](racks.md) R45 says. (S7, S8)
- **R18.** Arming a plug-in device for hot-swap ([device chains](device-chains.md) R19, [racks](racks.md) R44) opens the Plug-Ins label at the plug-in's row with its presets listed, and selects the preset the device last loaded, if it's there (L-BRW-015). (S7, S8)
- **R19.** An Audio Units preset file loads into the unit through its format, as the unit's saved state, and a factory preset through the unit's own list; the device takes the preset's name. A unit's factory presets are read-only: dragging one onto a browser folder saves nothing. (S7)
- **R20.** A preset's row key is its plug-in's row key (R11), `#preset/` and the preset file's path, or `#factory/` and the factory preset's number; `browser.open_folder`, `browser.select`, `browser.load_selected` and a drag take these keys, and `device.save_preset` writes a plug-in device's state. The loaded preset reads back through the query tool's `device` object (its preset name and state) and the browser's rows through `browser.state`. (S8)

**Architectures, and plug-ins a set names (Phase 10)**

- **R21.** The cache keeps, for each plug-in, the architectures its binary holds, read from its headers ([plug-in bridging](plugin-bridging.md) R1); a cache written before this rule is read again at the next scan, its entries without architectures described afresh. (WP-10.7) (S9)
- **R22.** A plug-in device that a set, a device preset, a rack preset, a DAWproject import or an installed pack names is found by its format and identifier in the scanner's cache, which holds only plug-ins in the folders R1, R10 and R12 search (each format's system, user and network folders, `CLAP_PATH`, `LV2_PATH`; Audio Units through the system's list of components). The file saved with a device ([CLAP hosting](clap-hosting.md) R8) is only a hint: it chooses between two cached files of the same plug-in, and, while the scan at start hasn't finished (R13), it is loaded if, with every link in it resolved, it lies inside a folder that scan searches for its format. (WP-10.8) (S9)
- **R23.** A hinted file that lies in the set's project folder, in a pack's folder, in the temporary folder, or anywhere outside the folders searched for its format is never loaded: the device is a missing plug-in ([CLAP hosting](clap-hosting.md) R12), keeping its state, and `plugin.info` and `plugin.list` give the reason `not_in_scanned_folders` with the file named. Nothing in a set, a preset, a pack or an imported file adds a folder to those searched. (WP-10.8) (S9)
- **R24.** A plug-in file dropped on Beatlayer, or named to `plugin.load`, that doesn't lie in a folder searched for its format is refused, with a message naming the format's folders and saying to install it there and rescan; one that does is scanned first and loaded by its identifier. (WP-10.8) (S9)
- **R25.** The test plug-ins are loaded through a test-only scanned folder given to the scanner by the tests, never through a hint outside the folders searched. (WP-10.8) (S9)
- **R26.** A plug-in with no code for Beatlayer's architecture but code a bridge runs is scanned by the scanner built for its architecture ([plug-in bridging](plugin-bridging.md) R4, R13); R3 and R4 hold for it, and R14 covers every scanner and host build the package holds ([plug-in bridging](plugin-bridging.md) R11, R14). (WP-10.7) (S9)
