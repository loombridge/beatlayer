# Macros: macro controls, Map mode, Randomize, and variations

- **Status:** implemented (R1 to R36 each have a passing test)
- **Work packages:** WP-5.4 (macros, Map mode, Randomize, names and colours, R1 to R20), WP-5.4b (the stepped and radio-button styles: R21 to R24), WP-5.5 (macro variations: R25 to R33), WP-7.3b (MIDI and key mapping of macros, and the Mapping Browser's modes: R34 to R36). The rack itself, its chains, its title bar and its view column are WP-5.1's and WP-5.2's ([racks.md](racks.md)); the map modes themselves are [map modes](map-modes.md)'s; rack presets are WP-5.8's; modulation of a macro or of a mapped parameter is [modulation.md](modulation.md)'s
- **Parity-matrix row:** Automation and modulation: Macros (16 per rack), variations, randomise, map mode with per-mapping ranges; [the improvements](../05-improvements.md), IMP-30 (stepped and radio-button macro styles)
- **Checked against:** the Live 12 reference manual (online edition), read 17 October 2026; the Live 12 release notes, 12.4

## The behaviour

Every rack has up to 16 macro controls: knobs of the rack's own that each move any number of parameters inside the rack at once. A new rack shows eight, and buttons in its macro view show more or fewer. In Map mode a person clicks a parameter inside the rack, then a macro's Map button, and the macro drives that parameter from then on over a range the mapping's Min and Max set; Min above Max turns the mapping round. The mappings list, which takes the browser's place while Map mode is on, lists every mapping with its range. A mapped parameter belongs to its macro: its own control can't be moved, though modulation still acts on it. A macro with one mapping takes its parameter's name and unit; with more, it's "Macro N" on a 0 to 127 scale. Macros can be renamed and coloured. The rack's Rand button sets its mapped macros to random values, skipping any excluded from it.

Variations are snapshots of a rack's macros: New stores the macros' values as a variation, Launch brings them back, Overwrite replaces what a variation holds, and a macro excluded from variations keeps its value when one is launched. Beatlayer adds two macro styles of its own (IMP-30): a stepped knob and a set of radio buttons, each offered beside Live's continuous knob, which stays the default.

This spec covers the macros in the document, in the engine and in the rack's macro and variations views, and their commands. Undo steps named in code type, such as `Map to Macro`, are Beatlayer's own names. It leaves the rack, its chains and zones to [racks.md](racks.md), and what a modulator or a clip envelope does to a macro or to a mapped parameter to [modulation.md](modulation.md).

## Rules

**The macros (WP-5.4)**

- **R1.** Every rack ([racks.md](racks.md): instrument, drum, audio-effect and MIDI-effect racks) has 16 macros, numbered 1 to 16. Each macro is a parameter of the rack, a continuous value along its control's travel from 0 to 1, which `device.parameters` lists for the rack and `device.set_param` sets, as for any device's parameter. (S1, S9)
- **R2.** A new rack shows macros 1 to 8 in its macro view (L-DEV-008). The view's Show More and Show Fewer buttons show one macro more or fewer, from 1 to 16, always the lowest-numbered ones (the step of one is Beatlayer's own). How many show is saved with the set; changing it, like showing and hiding a rack's views ([racks.md](racks.md) R19), isn't an undo step. A hidden macro keeps its value, its mappings and its automation, and still drives its parameters (Beatlayer's own). (S1, S5)
- **R3.** The macro view's Map switch turns the rack's Map mode on and off. While it's on, every parameter that can be mapped to this rack's macros (R4) is tinted with the theme's mapping colour, a Map button shows under each shown macro, and the mappings list takes the browser's place; turning it off, or turning on another rack's Map mode, puts the browser back. Map mode is view state: it isn't saved and isn't an undo step. (S2, S7)
- **R4.** A macro maps any parameter of any device inside its rack, at any depth: in any of its chains, and inside a rack nested in it, that rack's macros included. It also maps its rack's chain selector and its chains' mixer controls ([racks.md](racks.md)). It doesn't map its own rack's macros, a parameter outside its rack, or a device's parameter on another track. (S1, S2)
- **R5.** In Map mode, clicking a mappable parameter's control selects it (outlined, and changing nothing), and clicking a macro's Map button maps the selected parameter to that macro: one undo step, `Map to Macro`. A macro maps any number of parameters. A parameter is mapped to at most one macro of a rack: mapping it to another macro of the same rack moves its mapping there (Beatlayer's own). (S1, S2)
- **R6.** A new mapping's Min and Max are the bottom and top of the parameter's range. When it's the macro's only mapping, the macro first moves to the position that gives the parameter the value it has, so nothing jumps; when the macro already has mappings, the new parameter takes the value the macro gives it. Both are Beatlayer's own. (S2)
- **R7.** A macro at position `v` gives each mapped parameter the value at position `min + v · (max − min)` of the parameter's own travel, where `min` and `max` are the positions of the mapping's Min and Max on that travel (logarithmic where the parameter's taper is, [device-framework.md](device-framework.md) R1); a stepped parameter (a switch, a choice, a whole number) takes the step nearest. With Min above Max the parameter falls as the macro rises. The straight line in the parameter's travel is Beatlayer's own law. (S2, S9)
- **R8.** A macro's change reaches every mapped parameter on the macro's frame, at any block size, and a mapped continuous parameter glides from there as any change does ([device-framework.md](device-framework.md) R4, R6); a macro's envelope drives its parameters frame by frame ([automation.md](automation.md) R3). Nothing of this on the audio thread allocates, locks or blocks. (S9)
- **R9.** The mappings list shows, while Map mode is on, one row per mapping of the rack, in macro order and then in the order they were made: the macro, the device's name and the parameter's, Min and Max (each a number box in the parameter's own units, within its range). Setting Min or Max runs `rack.set_mapping_range`, one undo step; Min above Max is allowed and inverts the mapping. Invert Range, in a row's context menu, swaps Min and Max, one undo step (`rack.invert_mapping`). Delete, in the same menu or with the Delete key while a row is selected, unmaps that parameter, one undo step (`rack.unmap_macro`). (S2, S6)
- **R10.** A macro with exactly one mapping is named after its parameter and reads its value as the parameter's value text, in its unit. A macro with none, or with two or more, is named "Macro N" (its number) and reads its position on a scale of 0 to 127; with two or more whose parameters all share a kind, a unit and a range, it reads in that unit. A name given with Rename (R14) wins over all of these whatever the mappings. (S2)
- **R11.** A mapped parameter is held by its macro. Its control is drawn disabled, and a drag, the arrow keys, a double-click or Delete on it change nothing; `device.set_param` for it is refused, naming the macro. While the pointer is over it, or a gesture on it is refused, the Status Bar names the macro that holds it. Its own automation envelope stays in the set and doesn't drive it while it's mapped (Beatlayer's own); the macro's automation does. Clip envelopes and modulators still modulate it on top of the value the macro gives ([modulation.md](modulation.md)). Unmapping hands the parameter back at the value it has then (Beatlayer's own). (S2, S6)
- **R12.** A macro is automatable and modulatable like any device parameter (rule G2): the automation lane's device chooser lists the rack, its parameter chooser lists the macros by name, a hand move on an automated macro overrides its envelope ([automation.md](automation.md) R5), and moves while Automation Arm records are written as its envelope ([automation.md](automation.md) R17). (S8, S9)
- **R13.** Moving a macro, by its knob, the keys, or `device.set_param`, is one undo step named Change "<the macro's name>", however many parameters it moves ([device-framework.md](device-framework.md) R18); the mapped parameters' new values are part of that step and aren't steps of their own. (S9)
- **R14.** Rename (Cmd+R, M-EDIT-024, or the macro's context menu) gives a selected macro a name of its own, typed in place, Return to confirm and Esc to cancel; an empty name gives it back its default name (R10). Choosing a colour from the macro's context menu (the theme's palette, Beatlayer's own colours) colours its knob; None takes it away, as on a new rack. Edit Info Text (M-EDIT-025) gives the macro the user's own info text (L-INFO-003), which the Info View shows while the pointer is over it. Each is one undo step and saved with the set. (S2, S7)
- **R15.** The Rand button in the rack's title bar (`rack.randomize_macros`) sets every macro of the rack that has a mapping and isn't excluded from randomisation to a random position, as one undo step, `Randomize Macros`; macros with no mapping, and excluded ones, keep their values. Each macro moved is a hand move on it ([automation.md](automation.md) R5 and R17). The command takes an optional seed, and the same seed gives the same values; without one, Beatlayer picks a new seed each time. (S3)
- **R16.** Exclude Macro from Randomization, in a macro's context menu and ticked while it's on, switches that macro's exclusion: one undo step, saved with the set and with the rack in a preset. A new rack's macros aren't excluded. (S3)
- **R17.** The set saves, for each rack: every macro's value, its name where it has one, its colour, its info text, its style (R21), and its exclusions; how many macros show; and every mapping, as the macro, the device and parameter it maps, and Min and Max. A set saved before racks loads with none. A mapping that names a device outside its rack, a parameter the device doesn't have, a Min or Max outside the parameter's range, or a second mapping of one parameter in one rack doesn't load. (S1, S2)
- **R18.** A device that leaves its rack, by being deleted or moved out of it, takes its mappings with it in the same undo step, and a macro left with no mapping reads as R10 says. A rack that's copied, duplicated, cut and pasted, or moved keeps its macros, and its copy's mappings name the copy's own devices. (S1, S9)
- **R19.** Every action here is a registered command with a schema, a description and a permission class, run by ID through the agent API with the rack named, and each that isn't `read` names its readback: `rack.set_macro_count`, `rack.map_mode` (`read`, view state), `rack.map_macro`, `rack.unmap_macro`, `rack.set_mapping_range`, `rack.invert_mapping`, `rack.rename_macro`, `rack.set_macro_color`, `rack.set_macro_info_text`, `rack.randomize_macros`, `rack.set_macro_randomize_excluded` and `rack.set_macro_style`, each `edit`, and `rack.macros` (`read`), which reports each macro's number, name, colour, value and how it reads, style, exclusions, and mappings with their ranges, and how many show; the query tool's `device` gives the same in its `macros` field. A gesture in the macro view or the mappings list runs one of these. (S9)
- **R20.** In the macro view each shown macro is a knob with its name above and its value below, as a device's knob ([device-framework.md](device-framework.md) R16), its arc in its colour where it has one, and drags, steps and resets as a knob does ([device-framework.md](device-framework.md) R17). Assistive technology reads each as a slider with its name and value, and a mapped parameter's control as unavailable, with its macro's name. (S1, S9)

**Macro styles (IMP-30, Beatlayer's own; WP-5.4b)**

- **R21.** A macro's context menu has a Macro Style submenu, after the exclusion items, offering Knob, Stepped and Radio Buttons, with the current one ticked; every macro starts as a Knob, Live's continuous control, so nothing changes for a rack that never uses the menu. Changing the style is one undo step and saved with the set and with the rack in a preset. (S8)
- **R22.** A stepped macro has a number of steps from 2 to 16 (Steps, in the same submenu; 2 to 16 and the default of 8 are Beatlayer's own). Its position takes only the values `k / (steps − 1)`, `k` from 0 to `steps − 1`: a drag or an arrow key moves it a step at a time, `device.set_param` takes the nearest step, and a value set before it was stepped moves to the nearest step in the same undo step. Its automation lane has a stepped value axis, as a switch's does, and its envelope's and modulation's values play as the nearest step. (S8, S9)
- **R23.** A radio-button macro is a stepped macro drawn as its steps' buttons in the knob's place, in a column within the macro's slot, the lit button the current step and each labelled with the value text that step gives (R10); clicking a button moves the macro to that step. Assistive technology reads the buttons as a radio group named for the macro. (S8)
- **R24.** A style changes only how a macro is drawn and which positions it takes: a stepped or radio-button macro maps, automates, modulates, randomises (to a random step) and stores in variations as a knob does (rule G2). (S8)

**Macro variations (WP-5.5)**

- **R25.** The rack's Show/Hide Macro Variations view switch, in its view column ([racks.md](racks.md)), shows and hides the variations view beside the macro view; it's one of the rack's view switches and is kept as [racks.md](racks.md) keeps them. The view lists the rack's variations in the order they were made, each a row with its Overwrite button at its left, its name, and its Launch button at its right, with New above the list. (S4, S5)
- **R26.** New (`rack.store_variation`) stores every one of the 16 macros' values as a new variation at the end of the list, named "Variation N", N one more than the highest number among the rack's variations named that way: one undo step, `Store Macro Variation`. A rack holds any number of variations. (S4)
- **R27.** Launch (`rack.launch_variation`) sets every macro of the rack that isn't excluded from variations to the value the variation holds for it, at once and on one frame, as one undo step, `Launch Macro Variation`; excluded macros keep their values. Each macro it moves is a hand move on it, so its envelope is overridden ([automation.md](automation.md) R5) and, while Automation Arm records, the move is written as its envelope ([automation.md](automation.md) R17); continuous mapped parameters glide to their new values ([device-framework.md](device-framework.md) R4). (S4, S9)
- **R28.** Overwrite (`rack.overwrite_variation`) replaces every value a variation holds with the macros' values now, keeping its name and place: one undo step, `Overwrite Macro Variation`. (S4)
- **R29.** Clicking a variation's name selects it. Rename (Cmd+R, or its context menu) renames the selected variation, typed in place; Duplicate (Cmd+D, or its context menu) puts a copy with the same name and values straight after it (the name is Beatlayer's own) and selects the copy; Delete (the Delete key, or its context menu) deletes it. Each is one undo step (`rack.rename_variation`, `rack.duplicate_variation`, `rack.delete_variation`). (S4, S7)
- **R30.** Exclude Macro From Variations, in a macro's context menu and ticked while it's on (`rack.set_macro_variation_excluded`), keeps that macro from changing when any variation launches; storing and overwriting still record its value, so switching the exclusion off lets the next launch set it. One undo step, saved with the set. (S4)
- **R31.** The set saves each rack's variations in order, each with its name and the value of all 16 macros. A set saved before variations loads with none; a stored value outside 0 to 1 doesn't load. Copying a rack copies its variations. (S4, S9)
- **R32.** The variation commands are registered commands with schemas, descriptions and permission classes, run by ID with the rack and the variation named: `rack.store_variation`, `rack.launch_variation`, `rack.overwrite_variation`, `rack.rename_variation`, `rack.duplicate_variation` and `rack.set_macro_variation_excluded` are `edit`, `rack.delete_variation` is `destructive`, and `rack.show_variations` is `read` (view state). `rack.macros` reports each variation's name and values and each macro's variation exclusion, which is the readback the others name. (S9)
- **R33.** Launching a variation reaches every mapped parameter on one frame, with nothing allocated, locked or blocked on the audio thread: it sends parameter changes and no new program. (S9)

**MIDI and key mapping of macros (WP-7.3b)**

- **R34.** In MIDI Map Mode and Key Map Mode a rack's shown macros are mappable controls like any device parameter: a Knob or Stepped macro is a continuous control, mapped to MIDI only; a Radio Buttons macro is a radio button, mapped to MIDI or to keys, a key or note stepping it to its next button. A mapped macro moves its parameters as R7 says, and a run of messages to it is one undo step named as R13 names a macro's move. (S2, S8, S10; the kinds by style are Beatlayer's own)
- **R35.** A parameter a macro holds (R11) has no overlay in the map modes, and `remote.map` refuses it, naming the macro. A parameter that already has a MIDI or key mapping keeps it when a macro maps it, the mapping refused while the macro holds the parameter, and it acts again once the parameter is unmapped. (S10; Beatlayer's own)
- **R36.** The Mapping Browser is one list in the browser's place in three modes, one at a time: in a rack's Map mode it is R9's mappings list of that rack's macro mappings; in MIDI Map Mode and Key Map Mode it lists the set's MIDI or key mappings, a macro's showing its rack's path and its macro's name ([map modes](map-modes.md) R8). Turning on one mode turns off the others. (S2, S10)
