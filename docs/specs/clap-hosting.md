## The behaviour

A CLAP plug-in runs as a device in a track's chain, as any device does: in signal order, switched off and on, moved, deleted and brought back with undo, its parameters set by a person, by automation, or by an agent. The scanner (WP-2.9) now lists the plug-ins found on this machine under the browser's Plug-Ins label (see [the plug-in scanning spec](plugin-scanning.md)); a plug-in is also loaded from its file or bundle by path (`plugin.load`), which adds it to the selected track as `device.add` would. Its role comes from its features: an instrument, a MIDI effect (a note effect that isn't an audio effect), or an audio effect.

The plug-in processes the track's audio block by block, with each parameter change and each note on its own frame, and sends notes and its own parameter changes back out. Its automatable parameters are the device's parameters: the generic UI, `device.parameters`, and automation see them as they see a native device's. A change a person makes in the plug-in's own window comes back into the set as an undo step, as it does in Live. Its own state (whatever it keeps beyond its parameters) is saved with the set and comes back when the set is opened again. It reports its latency, which delay compensation (WP-2.11) will use, its gain adjustment where it implements CLAP's gain-adjustment metering extension (R21), and its editor opens in a window of its own titled as Live titles it.

A plug-in that offers the plug-in kit's agent-commands extension (every plug-in built on the kit does) brings its own commands, which agents reach through Beatlayer's agent API as commands of its device: listed, described, run, and scheduled like any other, each run one undo step labelled with the agent's name.

Plug-ins run inside Beatlayer's process until Phase 10's sandbox, so a plug-in that crashes takes the app with it. A plug-in that fails a call without crashing is contained: the song keeps playing, and the device says what went wrong. Export and agents' previews render with a registry of their own, so in them a plug-in device passes its input through; WP-2.6b lets offline renders run the live instances. A preset (`.blpreset`) holds parameter values only; a plug-in's own state in a preset comes with the plug-in presets of WP-2.9's browser.

## Rules

- **R1.** `plugin.load` loads a CLAP file or bundle by path and offers each plug-in in it as a device type: its CLAP ID as the device's kind, its name, and its role from its features (instrument; note effect and not audio effect, a MIDI effect; otherwise an audio effect). A file that isn't a CLAP plug-in is refused, and nothing changes. The plug-in chosen (by `plugin`, or the file's first) is added as `device.add` adds a device: one undo step, Insert Device, selected. (S1, S2, S5)
- **R2.** A plug-in device's node passes its input through until the main thread has activated the plug-in for it (at once when the compiler runs on the main thread, otherwise at the shell's next poll), then runs the plug-in on every block: the block's channels in and out of the plug-in's main ports, each of its channels taking the block's channel of its number. The plug-in's further audio output ports (WP-5.45) are rendered too, each of their channels taking the block's channel of its number and written into the block's buffer for that output, which another track takes as its input ([routing](routing.md) R12, R16); a plug-in with only its main port costs nothing for them. (S1, S2, S8)
- **R3.** A parameter change for a plug-in device reaches the plug-in on its exact frame within the block, from the document, automation, or an agent. (S1, S2)
- **R4.** Notes in a block reach the plug-in on their frames, and the notes it sends out go on from the node on their frames. (S2)
- **R5.** A plug-in's parameters are the device's: every one that's automatable, not hidden, not read-only, and has a range, in its order, as a continuous value over its range, or a whole number if it's stepped. `device.parameters`, the Device View's generic panel, and automation see them, each marked configured or not. **The configured list (WP-5.40, manual 24.1 and 24.1.2).** The device carries a list of the parameters its panel holds, in order. A plug-in with up to 64 modifiable parameters starts with them all on the list; one with more starts with none. The list belongs to the device and is saved with the set; every change to it is one undo step. **Configure mode.** The device's title bar carries the Configure switch (view state: it changes nothing in the set and isn't an undo step). While it is on, a parameter a person moves in the plug-in's own window joins the list, in the same undo step as the change. `plugin.move_configured_param` reorders the list and `plugin.unconfigure_param` removes an entry, each one undo step; removing one that has automation, a clip envelope, or a MIDI, key or Macro mapping is refused with what it has, as Live warns before deleting one, unless the command's `force` accepts the warning. **Outside configure mode,** a parameter moved in the plug-in's own window is a temporary entry in the automation and clip-envelope choosers; it is dropped when another parameter is moved, and choosing it in a chooser adds it to the list, so the choosers show the configured list and any temporary entry. **The panel.** The Device View's panel for a plug-in device is the D19 panel (WP-2.10, IMP-03): up to eight knobs showing the first eight entries of the configured list. `plugin.set_panel_param` overrides one knob with any of the plug-in's parameters (`index` is the knob, 0 to 7) and is remembered per plug-in in the preferences, not in the set; reordering or removing an entry moves the unremapped knobs with the list, and a knob's context menu offers the configured parameters and puts it back to following the list. The configured list itself is drawn in the generic panel and read by agents, not beside the knobs. Saving a configuration as a default (manual 23.2.6.2) needs a plug-in's configuration in presets, which isn't built. (S2, S5, S7)
- **R6.** A change a plug-in makes itself, such as from its own window, comes back into the set as one undo step named Change "<parameter name>": one for each gesture, with its final value, or one for each change outside a gesture. (S2, S3)
- **R7.** While a plug-in device is switched off, its parameter changes reach the plug-in through `flush`, so it comes back on with them. (S1, S2)
- **R8.** Saving the set takes each running plug-in's own state into it, with the file the plug-in came from, without an undo step; so does cutting, copying, or duplicating the device, so the copy starts from the state then. The set file holds the state in base64. A device whose plug-in isn't running keeps the state it had. (S1, S2)
- **R9.** When a set opens, each plug-in device's plug-in is loaded from its saved file and given its saved state. A state the plug-in refuses leaves it at its defaults, and `plugin.info` says so; `ClapHost::load_state` with a state it refuses changes nothing. (S2)
- **R10.** A plug-in reports its latency in frames when it's activated (the node's latency, and `plugin.info`'s). A plug-in that asks for a restart, or says its latency changed, is deactivated and activated again by the main thread; its node passes its input through for the blocks between. Delay compensation is WP-2.11's. (S1, S2)
- **R11.** Over a reopened plug-in's saved state, the set's parameter values are set before it's activated. (S2)
- **R12.** A plug-in that fails a call doesn't stop the song. One that can't be found or loaded, or refuses to activate, leaves its device passing its input through, keeping its saved state for the next save; one that fails while processing is never called again and its device is silent (as a native device after a panic, real-time rule 6). `plugin.info` reports each. A crash inside a plug-in ends the app until Phase 10's sandbox. (S1)
- **R13.** `plugin.show_window` opens the plug-in's editor or closes it, as the device's window button does: a wrench named Show/Hide Plug-In Window in its title bar, after the activator and the expand toggle and before the name (L-DEV-010), lit while the editor's window is open, and dimmed, but still drawn, for a plug-in without an editor that can open; where the plug-in supports CLAP's embedded API for the platform (win32, cocoa or x11), the editor opens in a window Beatlayer owns with the plug-in's view embedded (WP-2.10), and otherwise in a floating window of the plug-in's own, titled "<device>/<track>" as Live titles it; opening and closing aren't undo steps. On macOS Beatlayer's window is a utility panel above the main window with a small title bar (L-OTH-006), sized in points as the cocoa API measures; a plug-in is never told a scale there. An open editor window's place and size are saved with the set beside the document (WP-2.10), as a floating device's are (IMP-14), so it reopens where it was left; moving or resizing it is never an undo step. An open editor window follows View ▸ Plug-In Windows and the Auto-Hide Plug-In Windows setting like a floating device window (device-chains.md R31, R33): hidden while the toggle is off or while another track is selected, shown again when its track is re-selected or the toggle is turned on. Hiding isn't closing: the editor stays open, it isn't an undo step, and nothing in the set changes. (S2, S3, S4)
- **R14.** The host's main-thread calls run only on the thread that made it (CLAP's main thread), and are refused elsewhere. (S2)
- **R15.** A plug-in instance outlives its node: a chain edit compiles a program into which its node migrates still running; a device deleted has its plug-in deactivated on the main thread, and brought back by undo gets the same plug-in, with its state. (S1)
- **R16.** Loading, the window, the plug-in's status, the window's place, the panel's mapping, and configure mode are registered commands (`plugin.load`, External; `plugin.show_window`; `plugin.info`; `plugin.set_window`, Read, Device View; `plugin.set_panel_param`, `plugin.configure`, `plugin.configure_param`, `plugin.unconfigure_param` and `plugin.move_configured_param`, Edit, Device View), which agents run with the device named. Each configure command returns `device.parameters`, and `plugin.configure` returns the Device View's state. (S1)
- **R17.** Nothing the node does on the audio thread allocates, locks, or blocks: its buffers, event lists (1,024 events each way), and queues are made with it, an event past their room is dropped and counted, and the processor moves between threads through one-slot queues. (S1)
- **R18.** A plug-in that offers the agent-commands extension lists its commands when its instance starts. Each, except those in its `agent` area, joins the registry as a device command scoped to its device, `device.d<device>.<command>` (such as `device.d17.gain.reset`): labelled "<device>: <label>", with the plug-in's description and a sentence naming the device and its track, its schemas, and its permission class (External if it gives none), in the Device View context. `list_commands`, `describe_command`, `query` (a device's `commands`), `run`, and `schedule` reach them, and the agent API asks first or refuses by their class as for any command. They go when the device or its plug-in does, and come back when the plug-in starts again. (S6)
- **R19.** Running one runs the plug-in's command on the main thread and returns its result, or fails with the plug-in's reason. The parameters whose values it changed (read from the plug-in before and after) go into the set in one undo step named for the command, or in the agent's labelled step. The plug-in applies its own change from its next block and sends it as a gesture; a gesture that comes back with a value a command set is dropped, not made an undo step of its own. (S2, S6)
- **R20.** A control change, pitch bend or channel pressure in a block reaches the plug-in as a CLAP MIDI event (the message's raw bytes, on note port 0) on its frame, in order with the notes ([device framework](device-framework.md) R39). A plug-in that sends such messages out has them ignored. (S6)
**Per-note expression and MPE (WP-6.17b)**

- **R21.** While the device's MPE Mode is off ([MPE](mpe.md) R14, R15), a note's per-note pressure reaches the plug-in as a polyphonic key pressure MIDI event on note port 0, on the note's key and channel, on its frame; its per-note pitch and slide don't reach it. (S9, S10)
- **R22.** While MPE Mode is on, a plug-in whose note port takes CLAP's own note events gets each per-note expression as a CLAP note expression on its frame, for the note's port, channel, key and note ID: the pitch as tuning, in semitones; the slide as brightness and the pressure as pressure, each from 0 to 1. A plug-in whose note port takes only MIDI, or prefers MIDI-MPE, gets the notes and their expressions as MPE MIDI ([MPE](mpe.md) R17), as MIDI events on that port. (S9, S10)
- **R23.** While MPE Mode is on, the note expressions a plug-in sends out (tuning, brightness and pressure) go on from its node as per-note expressions of the notes it sent: tuning as a bend of its semitones over 48, brightness as slide and pressure as pressure ([MPE](mpe.md) R6, R20); MPE MIDI it sends out on a MIDI port is read as an MPE port's ([MPE](mpe.md) R11). (S9, S10)
- **R24.** A plug-in that implements CLAP's gain-adjustment metering extension (`clap.gain-adjustment-metering/0`, a draft extension) reports the gain adjustment it applied to the last sample of each block it processed, in dB (negative for a reduction). The host calls the extension's `get` on the audio thread after each block, and the device's node reports the value as its gain reduction (the mixer view spec, R40): a compressor or limiter plug-in then shows on its track's gain-reduction bar. A plug-in without the extension reports none, and so do VST3 and Audio Unit plug-ins, whose formats give the host no such call. (S11)
