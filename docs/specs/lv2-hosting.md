## The behaviour

An LV2 plug-in runs as a device in a track's chain, as any device does: in signal order, switched off and on, moved, deleted and brought back with undo, its parameters set by a person, by automation, or by an agent. Linux is where LV2 is: on macOS and Windows the module compiles to a stub that answers that LV2 isn't available. The host is Beatlayer's own, on the system's lilv library, which it loads when it first needs it, so a Linux machine without lilv runs Beatlayer with LV2 unavailable and adds nothing to the build. A plug-in is loaded by its bundle, an `.lv2` folder (`plugin.load`, which picks one of the bundle's plug-ins by URI and adds it to the selected track as `device.add` would), or found by the scanner in the folders `LV2_PATH` names, or the standard ones when it is unset. Its role comes from its class and ports: an instrument; a MIDI plug-in with no audio output a MIDI effect; otherwise an audio effect.

The plug-in processes the track's audio block by block through its audio ports, with each parameter change on its own frame, takes notes and channel messages and the song's position through its Atom ports, and sends notes back out. Its control input ports are the device's parameters: the generic UI, `device.parameters`, and automation see them as they see a native device's. Its own state (what it keeps beyond its control ports) is saved with the set and comes back when the set is opened again. Its latency port is the device's latency, which delay compensation (WP-2.11) uses. A plug-in with an X11 editor shows it in Beatlayer's X11 host window, and a change a person makes there comes back into the set as an undo step, as it does for a CLAP plug-in. Plug-ins run inside Beatlayer's process until Phase 10's sandbox, so a plug-in that crashes takes the app with it.

An LV2 instance has its sample rate fixed when it is made, and LV2 lets a plug-in's state be saved while it runs but not restored then. The host therefore never takes an instance back from a node: a state loaded into a running plug-in, a new node for a device, and an offline render's copy are each a new instance, started from the state the plug-in has. The instance a node held goes back to the main thread, which frees it.

## Rules

- **R1.** `plugin.load` loads an LV2 bundle by its folder (an `.lv2` folder) and offers each plug-in in it as a device type: its URI as the device's kind, its name, its role from its class and ports (an `lv2:InstrumentPlugin` is an instrument; a plug-in with a MIDI Atom port and no audio output is a MIDI effect; otherwise an audio effect), and whether it sends notes on from a MIDI Atom output, which lets it sit in the MIDI-effect position of a MIDI track's chain (IMP-24). A folder that isn't a bundle, or has no plug-ins, is refused, and nothing changes. The plug-in chosen (by `plugin`, a URI, or the bundle's first) is added as `device.add` adds a device: one undo step, Insert Device, selected. (S2, S8)
- **R2.** An LV2 device's node passes its input through until the main thread has made the plug-in's instance for it (at once when the compiler runs on the main thread, otherwise at the shell's next poll), then runs the plug-in on every block. The audio input ports (up to eight, other than side-chain inputs) each take the block's channel of their number, the last channel for more; a side-chain input hears silence. The main output ports (up to eight) write the block, each channel taking the output port of its number, the last output port for more; a plug-in with no audio output port writes silence. A device placed in the MIDI-effect position keeps the audio it receives and drops the plug-in's. (S1, S2, S8)
- **R3.** A parameter change for an LV2 device reaches the plug-in on its exact frame within the block, from the document, automation, or an agent, and so do the values automation and modulation give the parameters they drive (the modulation spec, R10): LV2 reads a control port once a block, so the block is run in parts, split at each frame a control port changes on, and each part sees the value that frame sets. (S1, S2)
- **R4.** Notes in a block reach the plug-in on their frames through its MIDI Atom input ports, as MIDI messages (a note-on, a note-off, and a choke as a note-off at velocity 0); a control change, pitch bend or channel pressure reaches it as the message's raw bytes, in order with the notes; and the notes it sends out of a MIDI Atom output port go on from the node on their frames, in the part of the block they were sent in. A plug-in that sends other messages out has them dropped. A plug-in whose Atom input takes `time:Position` is given the song's position at the first frame of each part of the block (its frame, whether it plays, the bar and beat, the signature and the tempo). A block's MIDI past 512 events is dropped and counted. (S2, S3)
- **R5.** A plug-in's parameters are the device's: every control input port that isn't kept off the plug-in's panel (`pprops:notOnGUI`) or from automation (`pprops:notAutomatic`) and has a range (a toggle or a choice needs none), in port order, each with its port number as its ID. A `lv2:toggled` port is a toggle; an `lv2:enumeration` port whose scale points count up by one from a whole number is a choice of their labels (the choice counts from 0, whatever number the first scale point has); an `lv2:integer` port is a whole number; a `pprops:logarithmic` port with a range above 0 is continuous over a logarithmic travel; anything else is continuous; the unit (`units:db`, `hz`, `ms`, `s`, `pc`, `semitone12TET`, `cent`) is the parameter's where Beatlayer has it. `device.parameters`, the Device View's generic panel, and automation see them, each marked configured or not, and the configured list, Configure mode and the D19 panel are [CLAP hosting](clap-hosting.md)'s R5. A range that depends on the sample rate (`lv2:sampleRate`) isn't scaled. (S2, S8)
- **R6.** A change a person makes in the plug-in's editor comes back into the set as one undo step named Change "<parameter name>": one for each gesture (the UI takes hold of a control with `ui:touch` and lets go), with its final value, or one for each write outside a gesture. A write to a port that is not a parameter reaches the plug-in and not the set. (S7, S8)
- **R7.** While an LV2 device is switched off, its parameter changes are kept and given to the plug-in at the first frame of its next block, so it comes back on with them. (S1, S8)
- **R8.** Saving the set takes each running plug-in's own state into it, with the bundle it came from, without an undo step; so does cutting, copying, or duplicating the device, so the copy starts from the state then. The state is the text lilv writes (the plug-in's control inputs and whatever its state interface stores), held in the set file in base64; it is saved while the plug-in runs, which LV2 allows. A device whose plug-in isn't running keeps the state it had. (S2, S6, S8)
- **R9.** The host gives a plug-in `urid:map` and `urid:unmap`; `options:options` with the block-size bounds (1 and the engine's maximum), the sequence size and the sample rate; `bufsz:boundedBlockLength`; `worker:schedule`, whose jobs run on a thread of the plug-in's own and whose answers reach the plug-in at the start of the next block, followed by `end_run`; and `log:log`, whose messages are dropped (a plug-in may log from its audio thread). A plug-in that needs another feature won't instantiate, and its device passes its input through (R12). (S2, S4, S5)
- **R10.** A plug-in reports its latency in frames through its latency port, which the node reads after each block (the node's latency, and `plugin.info`'s); a change is reported to the engine, which compiles with it, so delay compensation follows the plug-in (WP-2.11), and a node made after an engine restart reads the last latency at once. (S2, S8)
- **R11.** When a set opens, each LV2 device's plug-in is found by its URI among the plug-ins lilv knows, or in the bundle the set names, and made from its saved state; the set's parameter values go over the state. A state the plug-in refuses leaves it at its defaults, and `plugin.info` says so; `Lv2Host::load_state` with a state it refuses changes nothing. A state loaded into a running plug-in makes a new instance from it, which the node takes at its next block. (S2, S6, S8)
- **R12.** A plug-in that can't be found or won't instantiate leaves its device passing its input through, keeping its saved state for the next save, and `plugin.info` says why. LV2's `run` has no way to report a failure, so a plug-in that fails while running is not known to; a crash inside a plug-in running in Beatlayer's process (the Within Beatlayer hosting mode) ends the app, and one in a `beatlayer-host` process ends only that process, as [the plug-in sandbox](plugin-sandbox.md) R37 to R44 say. (S1, S8)
- **R13.** `plugin.show_window` opens and closes the plug-in's editor, as the device's window button does, for a plug-in with an X11 UI: the UI's library is loaded, the host window made, and the UI given its parent window, `ui:resize`, `ui:touch`, `ui:portMap`, `ui:idleInterface`, the plug-in's own handle (instance access), the options (scale factor, update rate, sample rate) and the URID map; the window takes the size of the UI's view, and follows the UI when it asks to resize (`ui:resize`); a window the person resizes tells the UI; the UI's idle call runs on each of the host's looks, and a UI that asks to be closed, or a window the person closes, closes the editor. Each control input's value reaches the UI as a `port_event` when it changes, and what the UI writes reaches the plug-in at the first frame of its next block and the set as R6 says; a value the UI wrote is not told back to it. When a new instance replaces the plug-in (a state loaded, a new node), the open editor opens again on it in the same window, and a gesture still held when an editor closes ends then, as a change of the set. A plug-in without an X11 UI keeps the D19 panel, and reports `has_window` false. The window follows View ▸ Plug-In Windows and Auto-Hide Plug-In Windows, hidden without being closed. Only the float protocol is understood: a UI that writes Atoms to the plug-in is ignored. (S7, S8)
- **R14.** The host's main-thread calls run only on the thread that made it, and are refused elsewhere. (S1, S8)
- **R15.** A plug-in instance outlives its node, as far as the state goes: a chain edit compiles a program into which its node migrates still running; a device deleted has its node dropped, and the instance goes back to the main thread to be freed there; brought back by undo, a new instance starts from the state the old one had. (S1, S6, S8)
- **R16.** Offline renders (exports, agents' previews, freezes and bounces) play LV2 devices through a copy of the plug-in made for the render, at the render's rate and block size, from the state the engine's plug-in has now and the rendered set's parameter values; the engine's instance is not touched, so it keeps playing and nothing the render does to its copy changes it; the copy is freed when the render's node lets go of it. A render of a set with no LV2 device lends nothing. (S6, S9)
- **R17.** Loading, the window, and the plug-in's status are the registered commands `plugin.load` (External), `plugin.show_window` and `plugin.info`, which agents run with the device named, for LV2 devices as for the others; the scanner's commands (`plugin.scan`, `plugin.rescan`, `plugin.list`) cover LV2 on Linux. (S1, S8)
- **R18.** Nothing the node does on the audio thread allocates, locks, or blocks: its buffers, event lists (512 MIDI events, 1,024 parameter changes), and queues are made with it; an event past their room is dropped and counted; the plug-in's instance is made and freed on the main thread; the worker's thread polls its queue and the audio thread never signals it. (S1)
- **R19.** LV2 is Linux only: on macOS and Windows `Lv2Host` answers that LV2 isn't available, the engine's registry offers no LV2 device types, the scanner does not scan LV2, and an LV2 device in a set opened there is unhosted and passes its input through. On Linux a missing lilv does the same. (S1, S2)

**In a sandbox process (Phase 10)**

- **R20.** An LV2 plug-in in a `beatlayer-host` process keeps R1 to R19, with its worker thread, its state and its Atom ports in the host; it renders exactly what it renders in Beatlayer's process, and an offline render makes its copy in the host from the plug-in's state ([the plug-in sandbox](plugin-sandbox.md) R27, R29). (WP-10.4) (S1, S8)
- **R21.** A set's LV2 device is found by its plug-in's URI among the bundles the scanner found in the folders it searches; a bundle the set saved as a hint outside them is never loaded ([plug-in scanning](plugin-scanning.md) R22 to R24). (WP-10.8) (S1)

## Tests

The test plug-in, Test Gain Echo, is built from source in `crates/test-lv2`, with its bundle's metadata generated in the build and no binary committed, and loaded from its bundle. It is an audio effect with a gain, a latency port, MIDI in and out (it echoes each note an octave up), a state of its own, one control port of each kind, a worker, `time:Position`, and an X11 UI scripted so a test sees every call between it and the host. The tests run where lilv is: on Linux always (a missing lilv fails them), and elsewhere when `BL_TEST_LILV` names a lilv library.
