# Agent permissions per call: edits over other clips, the person's gestures, and agents' tokens

- **Status:** implemented (R1 to R14 each have a passing test)
- **Work packages:** WP-1.15b (this spec) and WP-1.15c (its interface follow-up: R4's named clips, R11 to R13); WP-6.11 adds the MIDI Tools commands to R11; building on WP-1.15 (the agent API), WP-1.8b ([arrangement-editing](arrangement-editing.md)), WP-1.10 ([browser](browser.md)), and WP-1.18 (the transport in the app, [control-bar-transport](control-bar-transport.md))
- **Parity-matrix row:** none: the agent API is Beatlayer's own (D17). What an edit does to the set is Live's, through the specs it cites
- **Checked against:** the architecture's "Agent control" and the specs cited, 11 October 2026

## The behaviour

An agent asks the person before it deletes the person's work. WP-1.15 decided that by command: `track.delete` and `arrangement.delete` are destructive, `arrangement.move_clips` is an edit. But in the Arrangement a clip placed over part of another replaces the part it covers, as in Live, so a move, a resize, a nudge, a duplicate, a paste, a drop from the browser, or a MIDI file import can delete or shorten clips it never names. Beatlayer decides such a call's class from its arguments against the set as it is: placed over other clips, it's destructive as well as its own class and asks first, naming the clips it would replace or shorten; placed in empty space, it doesn't. Likewise `clip.set_data`, which replaces a MIDI clip's whole list of notes, asks first when it would leave the clip fewer notes than it has. The edit itself is exactly what the person's own edit does; the permission only decides who must agree.

While the person is dragging (clips, or a value such as a fader), the drag is one undo step in the making. An agent's call that comes meanwhile waits, with nothing on screen, and runs after the drop as its own undo step, labelled with the agent's name, so the person's drag and the agent's edit can be undone apart.

An agent's rights (connecting without being asked, and autonomous mode) belong to a token of its own, which Beatlayer makes when the person first allows it, not to the name its client gives. A client that connects with the agent server's token is asked about each time and is never autonomous, so a client presenting another agent's name gets none of its rights. The Settings window shows each allowed agent's token in its row under Allowed Agents, where the person copies it into the agent's client, with a New Token button to replace it.

And in the app, the engine the set plays through is the agent API's engine too: agents' transport and scheduled commands go on the queue the person's transport commands take, and scheduled commands fire on their exact frames as the agent's undo steps, as `bl-cli`'s engine harness plays them headless.

## Rules

- **R1.** A call's class is decided from its arguments against the set as it is when it runs. `arrangement.move_clips` (moving or copying), `arrangement.resize_clips`, `arrangement.nudge`, `arrangement.duplicate`, `arrangement.paste`, `track.paste_bounced_audio`, `browser.add_to_arrangement`, `browser.load_selected`, `midi.import_file`, and, in the Session View, `session.paste`, `session.duplicate`, `session.copy_to_arrangement` and `session.copy_to_session` ([second-window.md](second-window.md) R23) are destructive as well as their registered class when they would delete, shorten, or split a clip they don't act on, or replace the clip in a full slot; otherwise they keep their registered class. The clips a move, resize, or nudge acts on are the ones it names, or the selected ones; a copy, duplicate, paste, or drop acts on none of the clips already there. Every other command keeps its registered class, and no call's class is ever lower than its command's. (S2, S3, S4)
- **R2.** A call whose class is destructive or external asks the person first, as WP-1.15 does, unless the session has the rights of an agent the person made autonomous (R7, R8); headless, it's refused unless `bl-cli mcp` was started with `--autonomous`. A declined call changes nothing. An allowed one does exactly what the person's own edit does. (S1, S2)
- **R3.** A drop's or an import's files aren't read before the person allows it, since reading them is the external part, so `browser.add_to_arrangement`, `browser.load_selected` and `midi.import_file` are destructive when a clip on the track they land on ends after where they land; on a new track they never are. They're always external. (S3, S4)
- **R4.** The person's question names each command that asks with its classes, such as "Move Clips (destructive): …" or "Add Files to Arrangement (destructive and external): …", and its first line names every class among them. A command that would replace or shorten clips names them by name after its arguments, the clips the dry run's `replaces` lists, in the question's own style: "Move Clips (destructive): clips (…), to “5.1.1”. It replaces or shortens clip “B” and clip “C”.", and for a drop from the browser, whose files aren't read yet, "It may replace or shorten clip “Held”." (a clip without a name is "clip" and its ID). A dry run gives the call's classes (`permission`), whether it would run, ask, or be refused (`would`), and, for R1's commands, the clips it would replace (`replaces`). `list_commands` and `describe_command` mark R1's and R11's commands (`raised_by_arguments`), each saying what raises it. (S1, S6)
- **R5.** While the person's gesture is under way (a drag that edits the set, or a drag on a value), agents' tool calls wait, and nothing shows that they do, and so do the set's changes from scheduled commands that fire (the engine has already acted on the frame). When it ends, they run in the order they came. A call that asks first asks then, decided against the set as the drop left it, and what came after it waits for the answer. (S2, S4)
- **R6.** Each agent call that changes the set is one undo step of its own, labelled with the agent's name: "agent: label" for `run` (a batch, one document command, an Arrangement edit, or a drop), a checkpoint restore, and "agent: label at bar.beat.sixteenth" for a fired scheduled command. None joins the person's gesture's step. (S1, S2)
- **R7.** When the person allows an agent (answering Allow when it connects, or `agent.approve_client`), Beatlayer makes it a token of its own: 32 random bytes as 64 hexadecimal digits, kept in the OS keychain (one entry, service "Beatlayer Agent Server", account "tokens", holding the server's token and every agent's), never in the preferences' file, a command's result, a debug print, or a log. Tokens an older preferences file held move to the keychain at the next start, and the file is rewritten without them. Where the keychain can't be reached, the Status Bar says so and the tokens last until Beatlayer quits. A request carrying it is that agent's, whatever name its client gives: it isn't asked to connect again, and its undo steps carry the agent's name. Every request on a session must carry the credential the session started with. `agent.new_client_token` replaces an agent's token, and the old one is refused. Agents allowed before tokens existed get one when Beatlayer starts. (S4)
- **R8.** A client that connects with the agent server's token is asked about each time it connects. Allowed, it becomes the agent it names, with a token of its own (R7), if no allowed agent has that name; if one does, the session is allowed for itself only, with none of that agent's rights: never autonomous, and asking first for every destructive and external command. (S4)
- **R9.** Only a person changes what agents may do: every `agent.*` command, `agent.new_client_token` included, is refused to agents whatever token they carry. Each request's bearer token is compared with every token in constant time. (S1, S4)
- **R10.** While the app's audio engine runs on a device, the app's host attaches it to the agent API after every event and while scheduled commands wait (`Agent::sync_engine`): agents' transport commands and scheduled commands go on the engine's one queue, the queue the person's transport commands take, in the order they're sent; the engine's reports come back, and each fired scheduled command runs on the set as its agent's undo step; `transport`'s `status` shows the engine's transport. A new engine, after the device or the engine restarts, gets every command still waiting, once. Without a running engine, playback commands are refused and scheduled commands wait. (S1, S5)
- **R11.** `clip.set_data` is destructive as well as an edit when, tried against the set as it is when it runs, it would leave a MIDI clip fewer notes than it has. One that adds notes, keeps their count, replaces an audio clip's file, or would fail keeps its registered class. It asks first as R2 says, its question names the clip as R4 does, and its dry run's result gives its `permission` and, when it would delete notes, `fewer_notes` (the clip, how many notes it `has`, and how many it `leaves`). In a batch, each command is decided against the set as the batch found it. Tempo and time-signature changes delete nothing and keep their class. `midi_tool.apply`, `midi_tool.set`, `midi_tool.set_auto`, `midi_tool.reseed` and `midi_tool.randomize` are decided the same way ([midi-tools.md](midi-tools.md) R24). (S6, S7)
- **R12.** In the Settings window's Agents page, each allowed agent's row under Allowed Agents shows, under its name and autonomous switch, its own token, in a read-only field like the server's token's (selectable and copyable, with a Copy button beside it that puts the whole value on the clipboard), with a New Token button that runs `agent.new_client_token` for that agent; a request carrying the old token is then refused with 401. The row is three lines: the agent's name with its autonomous switch and Forget, then a Token line with New Token where the server's has it, then the field beside its Copy button, as the server's token is laid out. The Address and every token field is selectable and has a Copy button beside it. The field is labelled "Token: name" and the button "New Token: name" for assistive technology. The window reads the token from the agent settings, filled from the keychain, with `Secret::expose`, the only way to a token's text: no command's result carries it and a debug print shows "Secret(…)". (S4, S6)
- **R13.** The Agents page's note says what the person sees: "An agent you allow gets its own token and isn't asked again. Clients using the server's token are asked each time." (S6)
- **R14.** The built-in assistant's tool calls may give a new object's ID as `{"$new": "name"}` and refer to it in a later call of the same turn as `{"$ref": "name"}`, as an agent's calls may. The project issues each ID once, before the call's class is decided, so the class is decided from the arguments that run (R1). A name given twice, or a `$ref` to a name no `$new` made, refuses that call, and the refusal goes back to the model. (S1)
- **R15.** Recording captures input devices, a microphone included, so `transport.set_recording` is external whichever value it sets and asks first as R2 says; `transport.stop_recording` (read) stops a recording and never asks. The app's own Record controls run in the shell and record at once. (S1)
