## The behaviour

Beatlayer's Help menu keeps Live's order and leaves out what belongs to Ableton's services (D21). Read the Beatlayer Manual... opens Beatlayer's own manual, which ships in every package and works without a network. Join the User Forum... and Get Support open the project's own pages. Load Demo Set opens Beatlayer's own demo song as an untitled copy, so the original never changes.

The manual's chapters come in the order of Live's manual, so a Live user finds each topic where they expect it, with chapters of Beatlayer's own where they fit; its text is Beatlayer's own, written from Beatlayer's specs and behaviour. Its reference chapters (every command, every shortcut, every native device's parameters, every Settings page) are generated from the registry, the keymap, the device descriptors and the Settings model, so they never drift from the app.

## Rules

### The menu (WP-10.19)

- **R1.** The Help menu holds, in order: Search Commands… and a separator (IMP-16); Learn View; a separator; Load Demo Set; Read the Beatlayer Manual...; a separator; Join the User Forum...; Get Support; a separator; Check for Updates.... Pack Overview, Learn Live at ableton.com..., User Account and Licenses... and Purchase License... are left out (D21). (S1, S2)
- **R2.** Read the Beatlayer Manual... runs `help.open_manual` (`external`), which opens the manual's first page from the copy in the package in the system's browser; with `page`, a chapter and section, it opens that page there. Where a build has no copy (a development build run from the repository), it opens the published manual's address. (S2)
- **R3.** Join the User Forum... runs `help.open_forum` (`external`) and Get Support runs `help.open_support` (`external`), each opening an address fixed in Beatlayer's source in the system's browser: the forum's, and the project's support page. (S1)
- **R4.** Each of these commands names its readback as none: it opens a page outside Beatlayer and changes nothing Beatlayer reads. (S5)

### The manual (WP-10.19)

- **R5.** The manual is written in `manual/`: `SUMMARY.toml` lists its chapters in order, each with its title and its Markdown file, and marks the generated ones. The chapters follow the order of Live 12's manual, with Beatlayer's own chapters (agents and the assistant, Beatlayer's improvements, plug-ins in a sandbox, crash reports and updates) beside the topics they belong with. No text, figure or example comes from Live's manual. (S3, S4)
- **R6.** `cargo xtask manual [--out DIR]` builds the manual as HTML pages, with a sidebar of chapters, a search box working from an index of headings shipped with the pages, and Beatlayer's own simple style in its typeface and colours, light or dark as the system is, readable at a phone's width. (S4)
- **R7.** Four chapters are generated: the command reference (every registered command's label, description, permission class, contexts and shortcuts on macOS and Windows), the keyboard shortcuts by context, the device reference (each native device's description and a table of its parameters: name, range, unit, default and description), and the Settings reference (each page and its rows). `cargo xtask check` generates them again and fails when they differ from the committed ones; generated chapters are never edited by hand. (S5)
- **R8.** The build fails on a link inside the manual to a page or section that doesn't exist; links to other sites are listed, never fetched. (S4)
- **R9.** Every picture in the manual is made by `cargo xtask manual-pictures` from a UI script, in a fixed theme and size; running it again on the same platform gives the same files. (S4)
- **R10.** Every package holds the built manual: inside the app bundle's resources on macOS, beside the executable on Windows, and in the AppImage's and tarball's shared data on Linux. (S2)
- **R11.** The workflow that builds `main` publishes the manual to the project's site. (S2)
- **R12.** The manual describes only what Beatlayer does at the time it's built: a feature not yet built isn't in it. (S4)
- **R13.** In the accessibility tree the three items are menu items with their labels, as every menu item is. (S1)
- **R14.** Check for Updates... is [updates](updates.md) R9's. (S1)

### Load Demo Set (WP-10.24)

- **R15.** Load Demo Set runs `help.load_demo_set` (`edit`): with unsaved changes it asks first, as Open does ([the app shell](app-shell.md) R4), then opens the demo set from the package as an untitled copy, so a save asks where and the bundled original never changes, its samples read from the package. As Open does, it starts an empty undo history. An agent's `help.load_demo_set` is refused while the set has unsaved changes, as `set.open` is. (S5)
- **R16.** The demo set is made in code by `cargo xtask demo-set` from Beatlayer's native instruments, effects and racks, with any audio generated by scripts in `tests/fixtures/gen/` or taken from Beatlayer's own library; it holds no third-party audio. `cargo xtask package` bundles it with its files. (S4)
- **R17.** The demo set renders with no missing device and no missing file. (S4)
- **R18.** A lesson's `demo:` link runs `help.load_demo_set` ([the Learn View](learn-view.md) R9). (S5)
- **R19.** `help.load_demo_set` reads back through the query tool's `set` object (its name, its file, which is none, and its unsaved changes). (S5)
