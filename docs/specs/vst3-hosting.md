## The behaviour

A VST3 plug-in runs as a device in a track's chain, as any device does: in signal order, switched off and on, moved, deleted and brought back with undo, its parameters set by a person, by automation, or by an agent. It's loaded from its `.vst3` bundle or module by path (`plugin.load`), which adds it to the selected track as `device.add` would. Its role comes from the class's subcategories: an instrument, or an audio effect.

Beatlayer hosts a class as its `IComponent` and its `IEditController`, connected to each other through their connection points, with the host's component handler on the controller; the controller's parameters are the device's. The plug-in processes the track's audio block by block through `IAudioProcessor`, with each parameter change in the block's `IParameterChanges` on its sample offset and each note in the block's `IEventList` on its frame; the notes it sends out go on from the node on their frames. The node passes its input through until the main thread has activated the plug-in for it.

On macOS the host makes a `CFBundleRef` with Core Foundation and passes it to `bundleEntry`. A single-component class (its own `IEditController`) takes the same path as any other, and its state path gives it the component's state only; the test plug-in has no such class yet. `Vst3Host::load_state` loads a state while a plug-in runs, as the CLAP host does.

This part loads, describes, activates and processes, saves and restores the component's and the controller's state with the set, reports latency and restarts the plug-in when it asks for one — a changed latency reaching the engine's delay compensation — and brings a change the plug-in makes itself, such as from its own editor, back into the set as one undo step per gesture. The plug-in's own editor is the next part's (WP-2.10). The scanner finds VST3 plug-ins in the format's own user, system and network folders (WP-2.9).

## Rules

- **R1.** `plugin.load` loads a `.vst3` bundle or module by path and offers each audio module class in it as a device type: its class ID as the FUID string for the device's kind, its name, and its role from its subcategories (an instrument; otherwise an audio effect), and whether it sends events on from an event output bus, which lets it sit in the MIDI-effect position of a MIDI track's chain (IMP-24). A path that isn't a VST3 module, or a module with no audio classes, is refused, and nothing changes. The class is added as `device.add` adds a device: one undo step, Insert Device, selected. (S1, S2, S3)
- **R2.** A plug-in device's node passes its input through until the main thread has activated the plug-in for it (at once when the compiler runs on the main thread, otherwise at the shell's next poll), then runs the plug-in on every block: the block's channels in the plug-in's main audio input bus, and its main output bus back into the block's channels. (S1, S4)
- **R3.** A parameter change for a plug-in device reaches the plug-in on its exact frame within the block, through the block's `IParameterChanges`, as a normalized value over the parameter's plain range; a change kept while the plug-in wasn't running reaches it at the block's first frame. (S1, S4, S5)
- **R4.** Notes in a block reach the plug-in on their frames, in the block's input event list, and the notes it sends out go on from the node on their frames. (S4)
- **R5.** The controller's parameters are the device's: every one that's automatable, not hidden, not read-only, not a bypass, not a program change, and has a plain range, in its order; `device.parameters`, the Device View, and automation see them, each marked configured or not. Configure mode and the D19 panel are the CLAP hosting spec's R5, which this mirrors: the configured list saved with the device, the Configure switch, adding by moving a parameter in the plug-in's window, reordering, removing with the warning, the temporary chooser entries, eight knobs over the first eight entries, and `plugin.set_panel_param` remembered per plug-in. (S3, S5, clap-hosting R5)
- **R6.** A change a plug-in makes itself, such as from its own editor, comes back into the set as one undo step named Change "<parameter name>": one for each gesture — `beginEdit` to `endEdit`, taken with its final value in plain units — or one for each change outside a gesture. Each instance has a component handler of its own, so each change belongs to its device, and the values the node applies to the component are told to the controller, so its parameters are the device's. (S1, S3, S5)
- **R7.** While a plug-in device is switched off, its parameter changes reach the plug-in through the node's flush and wait for its next block's first frame, so it comes back on with them. (S1, S4)
- **R8.** Saving the set takes each running plug-in's component and controller state into it, with the file the plug-in came from, without an undo step; so does cutting, copying, or duplicating the device, so the copy starts from the state then. The set file holds the state in base64, and the bytes are the component's state and the controller's, each length-prefixed, after a `BLTV` magic; a single-component effect has one state, and its controller's part is empty. A device whose plug-in isn't running keeps the state it had. (S1, S2, S3)
- **R9.** When a set opens, each plug-in device's plug-in is loaded from its saved file and given its saved state: the component's first, the controller told what it means with `setComponentState`, then the controller's own. A state the plug-in refuses leaves it at its defaults, and `plugin.info` says so; `Vst3Host::load_state` with a state it refuses changes nothing. (S2, S3)
- **R10.** A plug-in reports its latency in frames when it's activated (the node's latency, and `plugin.info`'s). A plug-in that asks for a restart (`restartComponent`), or says its latency changed, is deactivated and activated again by the main thread; its node passes its input through for the blocks between, and a changed latency is reported to the engine, whose delay compensation follows it ([the delay compensation spec](delay-compensation.md) R6). A node the compiler makes later — after an engine restart, say — starts with the latency the plug-in last reported. (S1, S3)
- **R11.** Over a reopened plug-in's saved state, the set's parameter values are set on the controller before it's activated, and kept to reach the plug-in on its first block. (S2, S5)
- **R12.** A plug-in that fails a call doesn't stop the song. One that can't be found or loaded, or refuses to activate, leaves its device passing its input through, keeping its saved state for the next save; one that fails while processing is never called again and its device is silent (as a native device after a panic, real-time rule 6). `plugin.info` reports each. A crash inside a plug-in ends the app until Phase 10's sandbox. (S1)
- **R14.** The host's main-thread calls run only on the thread that made it (VST3's main thread) and are refused elsewhere. (S3)
- **R16.** `plugin.load` and `plugin.info` are the registered commands agents run for a VST3 device: `plugin.load` is External, like any load, and `plugin.info` is a read. `plugin.info` reports the device's class ID, its file, whether it's active and for which settings, its latency, what went wrong if anything, its controller's parameter values in plain units, and that it has no editor until WP-2.10. (S1)
- **R17.** Nothing the node does on the audio thread allocates, locks, or blocks: its buffers, parameter queues and event lists are made with it, and a change or event past their room is dropped and counted. (S1)
- **R18.** A control change, pitch bend or channel pressure reaches a plug-in through its controller's MIDI mapping (`IMidiMapping`), as VST3 has hosts do it: the parameter the controller maps the message's controller to (bus 0, the message's channel, the controller's number, 128 for channel pressure and 129 for pitch bend) takes the message's value, normalized (the value over 127, a bend over 16,383), on the message's frame. The mapping is asked once, when the plug-in is activated. A message the controller doesn't map is ignored. A parameter's queue holds 64 points in a block; a message past that is dropped and counted. (S6)

**Per-note expression and MPE (WP-6.17b)**

- **R19.** While the device's MPE Mode is off ([MPE](mpe.md) R14, R15), a note's per-note pressure reaches the plug-in as a `PolyPressureEvent` for the note's channel, pitch and note ID, on its frame; its per-note pitch and slide don't reach it. (S7, S8)
- **R20.** While MPE Mode is on, a plug-in whose controller implements `INoteExpressionController` gets the note's expressions as `NoteExpressionValueEvent`s for its note ID, on their frames: the pitch as the tuning type, normalized as 0.5 plus its semitones over 240; the slide and the pressure as the types its `INoteExpressionPhysicalUIMapping` gives a key's Y movement and its pressure; the pressure as a `PolyPressureEvent` where it maps none to pressure, and the slide not at all where it maps none to Y movement. A plug-in whose controller has no note expression gets MPE MIDI ([MPE](mpe.md) R17) through its MIDI mapping: each note on its member channel, and that channel's pitch bend, controller 74 and channel pressure setting the parameters the mapping assigns for that channel, as R18 says. (S5, S7, S8; preferring note expression to the MIDI mapping is Beatlayer's own)
- **R21.** While MPE Mode is on, the note expression values a plug-in sends out go on from its node as per-note expressions of the notes it sent: tuning as a bend of its semitones over 48, and the types its physical mapping gives Y movement and pressure as slide and pressure ([MPE](mpe.md) R6, R20). (S7, S8)

## Tests

The test plug-in, Test Gain Echo, is built from source in `crates/test-vst3` and loaded by path as a VST3 bundle the tests assemble from its cdylib. It applies its gain from the exact frame of each parameter change, delays its audio by the latency it reports, adds a note-on's velocity to its output on the note's frame, and echoes every note an octave up on its frame; it saves and loads its gain, latency and last note, its controller performs a gesture on Last Note when a test hands it one (standing in for its editor, WP-2.10), and two states make it fail on purpose.
