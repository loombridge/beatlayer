## The behaviour

A plug-in is someone else's code, and a plug-in that crashes inside Beatlayer's process takes the song with it. Beatlayer therefore runs plug-ins in `beatlayer-host`, a child process, as it already scans them in `beatlayer-scan`. When a plug-in in a host crashes, hangs or misbehaves, only its host goes: its devices fall silent, the rest of the song plays on to the frame, the Status Bar and the device say which plug-in stopped, and Reload brings it back with the newest state Beatlayer kept of it.

The two processes share a region of memory for each host. Each block, the engine writes a sandboxed plug-in's audio, notes, parameter values and transport into the plug-in's slot, wakes the host, and reads the plug-in's output back from the same slot. The audio thread never waits for the host in a system call: it posts the block, runs other tasks while the host works, and then spins with a deadline for the result, as it already spins for its workers. So a sandboxed plug-in adds no latency; a block that isn't back in time plays silence for that plug-in and is counted. Requests outside real time (loading, state, parameter lists, editors, offline renders) travel over a control channel.

Settings ▸ Plug-Ins chooses how plug-ins are grouped into hosts, with a Plug-In Hosting chooser: Within Beatlayer (in Beatlayer's own process, as before), Together (one host for them all), By Plug-In (one host per plug-in type, in a new install) and Individually (one host per instance). A plug-in device's title-bar menu can override the setting for that device. ARA plug-ins stay in Beatlayer's process whatever the mode, because they read the set's audio through the host, and plug-ins built for another architecture always run in a host of their own architecture ([plug-in bridging](plugin-bridging.md)).

A sandboxed plug-in's editor opens from the device's wrench as an in-process one does. On Windows and Linux the host's view is embedded in Beatlayer's editor window; on macOS, where one process can't embed another's view through public interfaces, the host opens the editor in a panel of its own that keeps with Beatlayer's windows.

## Rules

### The two processes (WP-10.1)

- **R1.** A sandboxed plug-in runs in a `beatlayer-host` process, a child of Beatlayer started from the executable packaged beside Beatlayer's own. A host is given its instances' plug-in files and saved state, and nothing of the set (R16). One host may hold several instances, as the hosting mode decides (R33). (S1)
- **R2.** Beatlayer makes one shared-memory region for each host when it starts the host: an anonymous memory file on Linux (`memfd_create`), a POSIX shared-memory object on macOS (`shm_open`), and a file mapping on Windows (`CreateFileMappingW`), handed to the host by an inherited descriptor or handle. The region has a fixed, versioned layout that is the same on every architecture: fields at fixed offsets, little-endian, sized independently of the pointer width, and no pointers. It holds a header (the layout's version and hash, the heartbeat, R8) and one slot per instance, sized when the slot is made from the stream's largest block (4,096 frames) and the instance's ports and channels (up to 32 channels a port). Each slot holds the input and output audio of every port, a sequence number in each direction, and bounded single-producer, single-consumer rings: into the host, notes, note expressions, channel messages, parameter values and the transport; out of it, notes, note expressions, parameter gestures, and latency and restart requests. (S1, S6, S7, S8)
- **R3.** Audio crosses the region unchanged, bit for bit, and every event crosses on its frame, in order. An event that finds its ring full is dropped and counted, as a plug-in's event lists drop theirs ([CLAP hosting](clap-hosting.md) R17). (S1, S11)
- **R4.** Posting a block writes the slot, raises its sequence number, and wakes the host with a call that never blocks: a wake on a futex word in the region, shared and not private, on Linux (`FUTEX_WAKE`); a signal on a semaphore handed to the host at the handshake on macOS; `SetEvent` on an inherited event on Windows. The host's audio thread sleeps on the matching wait. Nothing on Beatlayer's audio thread waits in a system call for a host. (S1, S7, S8)
- **R5.** Collecting a block reads the slot's reply sequence number. Until it matches the block's, the collecting thread spins, reading the monotonic clock, up to the block's deadline (R22). A reply that arrives after its deadline is never read: the next post's sequence number tells it apart. (S1, S2)
- **R6.** Requests outside real time (loading, activating and deactivating, state, parameter lists, editors, offline renders, a plug-in's agent commands, shutting down) travel over a control channel: a Unix domain socket on Linux and macOS, a named pipe on Windows. Each frame is a length, a JSON header and raw bytes for state. A frame's header is at most 64 KiB and its bytes at most 64 MiB; a longer frame is refused from its length, before anything is allocated for it, and so is a header that doesn't parse as one of the protocol's messages. The audio thread never touches the control channel. (S3)
- **R7.** Beatlayer starts a host with the region, the control channel and the wake signal, and the host's first message is a handshake giving the protocol's version, the region's layout hash and the page size. A host whose version or layout differs from Beatlayer's is stopped, and each plug-in meant for it is a plug-in that couldn't be loaded ([CLAP hosting](clap-hosting.md) R12), `plugin.info` saying why. (S3)
- **R8.** A supervisor thread in Beatlayer watches each host's process (a process descriptor on Linux, a process event on macOS, the process handle on Windows) and the heartbeat the host's main thread advances in the region's header. A host that exits, or whose heartbeat stops for longer than the hang time (R37), is reported dead within 100 ms of its exit, or of the hang time running out; the engine learns it through an atomic flag it reads each block, never by waiting. (S1)
- **R9.** The tests use an echo host, a test-only build of the host that copies every slot's input to its output and its events back, and that can be told to delay, to stall, to crash, or to send malformed frames and ring entries. Nothing but the tests starts it. (Beatlayer's own testing rule, as [plug-in scanning](plugin-scanning.md) R5's)

### Hosting CLAP and VST3 plug-ins (WP-10.2)

- **R10.** `beatlayer-host` is a second executable of `bl-plugin-host`, beside `beatlayer-scan`, packaged and signed with the app as the scanner is ([plug-in scanning](plugin-scanning.md) R14). Its main thread is the format's main thread for every instance in it ([CLAP hosting](clap-hosting.md) R14); its audio thread runs the blocks of its instances, each in its own slot. (S1, S4)
- **R11.** A plug-in in a host behaves as it does in Beatlayer's process: [CLAP hosting](clap-hosting.md) R1 to R24 and [VST3 hosting](vst3-hosting.md) R1 to R21 hold for it, except where this spec says otherwise, and a sandboxed device renders exactly what the same device renders in process, to the bit, at any block size. (S11)
- **R12.** A sandboxed plug-in device's node passes its input through until its host has activated the plug-in for the node's rate and largest block and given it a slot, as an in-process node waits for its plug-in ([CLAP hosting](clap-hosting.md) R2). From then on, each block it writes the block's audio, notes, channel messages, the parameter values played at their frames (automation and modulation are worked out in Beatlayer's process, as for an in-process plug-in, and only their values cross) and the transport into the slot, posts, and later collects (R21). (S1, S11)
- **R13.** A sandboxed plug-in's own state is asked for over the control channel whenever an in-process plug-in's would be taken: at each save, cut, copy and duplicate ([CLAP hosting](clap-hosting.md) R8). Its saved state goes to the host with its activation request ([CLAP hosting](clap-hosting.md) R9, R11). A state request a host doesn't answer within 5 seconds takes the newest snapshot instead (R43). (S4, S5, S11)
- **R14.** The host sends a plug-in's parameter list at activation and whenever the plug-in says it has changed. Changes the plug-in makes itself (CLAP's gestures, VST3's `beginEdit`, `performEdit` and `endEdit`) cross the slot's out ring to Beatlayer's main thread, so each gesture is one undo step, as in process ([CLAP hosting](clap-hosting.md) R6). (S4, S5, S11)
- **R15.** A latency change or a restart a sandboxed plug-in asks for crosses to Beatlayer, which recompiles with the new latency, as in process ([CLAP hosting](clap-hosting.md) R10; [delay compensation](delay-compensation.md)), the node passing its input through until the host has the plug-in active again. (S4, S11)
- **R16.** A host never opens the set file, the project folder, the preferences, the journal or another instance's state: it is given only its own instances' plug-in files and state, and gives back only what R2 and R6 carry. (S3)
- **R17.** A VST3 plug-in's component and its edit controller both live in the host. (S5)
- **R18.** `plugin.info` reports each plug-in device's process: `in_process`, or the host's ID and its process ID, with the hosting mode that put it there (R33, R34), and why a device runs somewhere other than its mode says (ARA, R31; a bridged plug-in, [plug-in bridging](plugin-bridging.md) R5; three crashes, R42; the quirks list, [plug-in compatibility](plugin-compatibility.md) R21). (S11)

### In real time (WP-10.3)

- **R19.** A host's audio thread runs at real-time priority. On macOS it joins Beatlayer's output device's audio workgroup: Beatlayer sends the host a port for the workgroup over the control channel when a stream starts (`os_workgroup_copy_port`), and the host makes the workgroup from it and joins it, leaving it before the thread ends, as [the architecture](../02-architecture.md)'s real-time rule 7 says of Beatlayer's own threads. On Windows the thread registers with MMCSS as Pro Audio. On Linux it sets `SCHED_FIFO` where the rtprio limit allows; otherwise the host lowers its own `RLIMIT_RTTIME` hard limit and asks rtkit, so a plug-in that spins at real-time priority past the limit ends only its host, never Beatlayer. When the stream moves to another device, the host is sent the new workgroup and joins it. (S1, S6, S7, S8)
- **R20.** Where a host can't join the workgroup (a host for another architecture, [plug-in bridging](plugin-bridging.md) R7), its audio thread keeps its real-time priority without it, and `plugin.info` says which it has: the priority class, and the workgroup joined or not. (S6)
- **R21.** A sandboxed plug-in splits its track's segment task in two stages. The first runs the chain up to the plug-in and posts its block; the thread then goes on to other ready tasks. The second, which waits on the host's reply, collects the block and runs the rest of the chain and the track's mixer; the tasks that depend on the track wait on the second stage. A segment with several sandboxed plug-ins splits at each. The summing order doesn't change, so a set renders to the bit as it does with every plug-in in process, with any number of workers and at any block size, and no latency is added. (S2)
- **R22.** A block's deadline is its start plus 75 % of its period, read from the monotonic clock. A sandboxed plug-in whose block isn't back by its deadline plays silence for that block (its node writes zeros to its outputs and sends no events on), and the block is counted late for its device. The next block posts as usual. (S1, S2)
- **R23.** Eight late blocks in a row from one host, or 32 within a second, report the host as hung (R37). (S1)
- **R24.** Posting and collecting allocate nothing, take no lock, and make no call that can block: the wake (R4) is the only system call on the audio thread, and it returns at once, as a worker's wake does. (S1)
- **R25.** An offline render's blocks never run on a host's real-time thread (R29). (S1)

### Other formats, ports, renders and commands (WP-10.4)

- **R26.** Audio Units v2 run in a host on macOS, as CLAP and VST3 plug-ins do. Audio Units v3 are made out of process by the system (`kAudioComponentInstantiation_LoadOutOfProcess`) and are driven from Beatlayer's process, so a v3 unit that crashes takes only the system's process for it; a v3 unit's custom view is shown as [Audio Unit hosting](au-hosting.md) R22 says. (S6, S11)
- **R27.** LV2 plug-ins run in a host on Linux, with their worker thread, their state and their Atom ports in the host ([LV2 hosting](lv2-hosting.md) R20). (S11)
- **R28.** A slot carries every port configuration an in-process plug-in has: sidechain inputs ([routing](routing.md) R22 to R31), further audio outputs ([CLAP hosting](clap-hosting.md) R2), per-note expressions with their note IDs ([CLAP hosting](clap-hosting.md) R21 to R23, [VST3 hosting](vst3-hosting.md) R19 to R21), and channel messages ([CLAP hosting](clap-hosting.md) R20). (S11)
- **R29.** An offline render borrows a sandboxed plug-in through a control-channel request: the host deactivates the instance, activates it for the render's rate and largest block, processes the render's blocks through the same slot outside real time, on a thread of its own, and on the render's end restores it as [offline plug-in renders](offline-plugin-renders.md) R4 says. An LV2 plug-in renders through a copy made in the host from its state ([offline plug-in renders](offline-plugin-renders.md) R12). (S11)
- **R30.** A sandboxed plug-in that offers the plug-in kit's agent-commands extension lists and runs its commands through the control channel, so they join the registry and read back as an in-process plug-in's do ([CLAP hosting](clap-hosting.md) R18, R19). (S11)
- **R31.** A plug-in that answers ARA's entry points runs in Beatlayer's process whatever the hosting mode and the device's override ([ARA hosting](ara-hosting.md) R14); `plugin.info` gives its process as `in_process`, with the reason `ara`. (S11)

### The hosting modes (WP-10.5)

- **R32.** Settings ▸ Plug-Ins has a Plug-In Hosting section after Plug-In Windows (L-SET-017), with one row, Plug-In Hosting, a chooser of Within Beatlayer, Together, By Plug-In and Individually. By Plug-In is chosen in a new install. The choice is kept in the preferences, set by `plugin.settings`' `hosting` and read back from it. (S9, S10)
- **R33.** Within Beatlayer runs every plug-in in Beatlayer's process, as before the sandbox. Together runs every sandboxed plug-in in one host. By Plug-In runs one host for each plug-in type (its format and identifier), shared by every instance of it. Individually runs one host for each instance. Plug-ins built for another architecture are hosted as [plug-in bridging](plugin-bridging.md) R5 says, and ARA plug-ins as R31 says. (S1)
- **R34.** A plug-in device's title-bar menu has a Plug-In Hosting submenu ([device chains](device-chains.md) R45): Default (the setting's mode, named in brackets), then the four modes, the device's choice ticked. Choosing one is saved with the set as the device's override and is one undo step, Change Plug-In Hosting; `plugin.set_hosting` with a `device` sets it, and without one sets the global setting. (S10)
- **R35.** When the setting or an override changes, each instance whose process it changes moves: its state is taken, a new instance is made in its new process from that state with the set's parameter values over it, activated, and given the node, and the old instance is deactivated and freed; the node passes its input through meanwhile. The device's ID, its place in the chain and its parameter values don't change. (S11)
- **R36.** A plug-in that can't be started in a host (its host refused, R7) is a plug-in that couldn't be loaded ([CLAP hosting](clap-hosting.md) R12); it never falls back to Beatlayer's process by itself. (S3)

### Crashes and hangs (WP-10.5)

- **R37.** A host has crashed when its process ends without Beatlayer asking it to, or when it sends a message R57 refuses. It has hung when a control request goes unanswered for 10 seconds, when its heartbeat stops for 10 seconds, or when R23 reports it; Beatlayer then kills it and treats it as crashed. Beatlayer never waits on its main thread for a dead or hung host. (S1, S3)
- **R38.** When a host crashes, every node of its instances plays silence from the next block, without the engine waiting, and the rest of the song plays on exactly as it would have: every other track's render is unchanged to the frame. (S1, S2)
- **R39.** The Status Bar's message area (L-STAT-002) says that the plug-in stopped working, naming it and its track ("Test Gain Echo on 2-MIDI stopped working."); when one host held several devices, it names the first and how many more. Clicking the message selects the first device. (S10)
- **R40.** A crashed plug-in device's panel shows, in place of its knobs, a notice that the plug-in crashed (or stopped responding, for a hang) and a Reload button; while the plug-in has crashed, its title-bar menu has Reload Plug-In ([device chains](device-chains.md) R46). The device keeps its parameters, automation and mappings, and passes nothing until it's reloaded. (S10)
- **R41.** Reload (the notice's button, the menu item, `plugin.reload` for a device) starts a new host for the instances of the crashed host, restores each from its newest snapshot (R43) with the set's parameter values over it, and activates it. The restored state becomes each device's saved state in one undo step, Reload Plug-In. Nothing reloads by itself. (S11)
- **R42.** A plug-in type that has crashed three times in a session runs Individually for the rest of the session, whatever the setting and the overrides, and its notice says so. (S1)
- **R43.** Beatlayer keeps a snapshot of each sandboxed instance's state on its main thread: taken at every save, cut, copy and duplicate, when a gesture ends, and, at most once a second, when the plug-in says its state has changed (CLAP's `mark_dirty`, VST3's `setDirty`), never on the audio thread. A host that crashes during a save's state request still lets the save finish, with the newest snapshot. (S4, S5)
- **R44.** A reload or a move (R35) never reorders the chain or changes a device's ID. (S11)
- **R45.** `plugin.info` reports for each plug-in device whether it has crashed or hung, its crashes in this session, its late blocks, its process, its mode and the snapshot's time. (S11)

### Editors from another process (WP-10.6)

- **R46.** `plugin.show_window` opens and closes a sandboxed plug-in's editor as [CLAP hosting](clap-hosting.md) R13 says of an in-process one: from the device's wrench, titled "<device>/<track>", its place and size saved with the set, never an undo step. R47 to R49 say how each platform shows it. (S4, S5, S11)
- **R47.** On Windows the host makes the plug-in's view in a child window that Beatlayer's editor window adopts across processes, their input queues joined only while the editor is open and parted when it closes. Where adopting a window across processes loses the keyboard focus or input-method text, the host's own top-level window is used instead, owned by Beatlayer's main window so it keeps above it; WP-10.6 measures both and this rule records the one built. (S7)
- **R48.** On Linux Beatlayer sends the host its editor window's X11 ID and the host embeds the plug-in's view in it, as an in-process plug-in's is embedded; under Wayland through XWayland, as now. (S4, S5)
- **R49.** On macOS the host opens the editor in a utility panel of its own, titled and sized as Beatlayer's panel for it would be and placed where the set saved it. It keeps above Beatlayer's main window but not above other applications, hides while Beatlayer is hidden or another application is active, and takes key status only when it's clicked, never from a text field in Beatlayer. (S6, S10)
- **R50.** Multiple Plug-In Windows, Auto-Hide Plug-In Windows and Auto-Open Plug-In Windows, View ▸ Plug-In Windows and View ▸ Close All Plug-in Windows act on sandboxed editors as on in-process ones ([device chains](device-chains.md) R31, R33, R40). (S9, S11)
- **R51.** A key typed into a sandboxed editor that the plug-in doesn't take reaches Beatlayer's keymap, as from an in-process editor, so the transport's keys keep working. (S4, S5)
- **R52.** A resize the plug-in asks for, and a resize of the window, reach the other side; a change of the screen's scale factor reaches the plug-in where its format takes one. (S4, S5)
- **R53.** A host that crashes takes its editors with it and leaves no window behind; once the device is reloaded its editor opens again from the wrench. (S11)

### What a host is given (WP-10.29)

- **R54.** A host inherits only its region, its control channel, its wake signal and its standard streams: every other descriptor is closed on exec on Linux and macOS, and on Windows the host is started with an explicit list of the handles it inherits. Nothing secret is on its command line. (S3, S7)
- **R55.** A host's environment holds only: the locale (`LANG`, `LC_*`), the home and temporary folders (`HOME`, `TMPDIR`, `USERPROFILE`, `TEMP`, `TMP`, `APPDATA`, `LOCALAPPDATA`), the display (`DISPLAY`, `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`), `PATH`, the plug-in path variables (`CLAP_PATH`, `VST3_PATH`, `LV2_PATH`), and the variables Windows itself needs (`SystemRoot`, `windir`, `ProgramFiles`, `ProgramFiles(x86)`, `CommonProgramFiles`, `ProgramData`). Nothing that names a token or a key reaches it. Its working folder is its own, inside the app's data folder. (S3)
- **R56.** A host isn't confined by the operating system: a plug-in in it can read and write what the person can, as plug-ins need their licence files and preset folders. [The security page](../security.md) says so. (S3)
- **R57.** Beatlayer treats everything a host sends as untrusted: each control frame within R6's caps and of a known shape; each ring entry read within its bounds (indices inside the slot, counts within the ring, parameter IDs that instance has, note IDs and keys in range, a latency of at most 2^20 frames, a state within R6's cap). A message that breaks one is refused, and the host is treated as crashed (R37), with no panic in Beatlayer. (S3)
- **R58.** A fuzz target, `sandbox_messages`, feeds the control channel's decoder and the ring readers on Beatlayer's side arbitrary input, and the weekly fuzz workflow runs it. (S3)
- **R59.** [The security page](../security.md)'s Plug-ins row and gaps say what the sandbox guards and what a plug-in in a host can still do. (S3)

### Commands, readback and assistive technology

- **R60.** Every action is a registered command with a schema, a description and a permission class: `plugin.settings`' `hosting` (`edit`, a kept preference; WP-10.5), `plugin.set_hosting` (`edit`; WP-10.5), `plugin.reload` (`edit`; WP-10.5); `plugin.info` (`read`) reports R18, R20, R31 and R45's fields. Each command that isn't `read` names its readback. (S11)
- **R61.** In the accessibility tree, the Plug-In Hosting chooser is a pop-up button named Plug-In Hosting with its value; the crash notice is a group naming the plug-in and what happened, with Reload a button; the Plug-In Hosting submenu's items are radio items. (Beatlayer's own names)
