## The behaviour

A control surface is a MIDI controller Beatlayer drives as a whole rather than one mapped control at a time. On the Tempo & MIDI page of the Settings, the Control Surfaces table has six rows; each picks a surface by name and the MIDI input and output it talks on, and a Dump button sends the controller a setup where the surface has one. A surface chosen there owns its ports: what arrives on its input goes to the surface, which turns presses and turns into Beatlayer's commands, and what it sends back lights the controller's buttons and moves its displays. The mappings a person makes by hand in MIDI Map Mode still win over the surface's own.

Each surface runs inside Beatlayer's control-surface host, on a thread of its own, away from the audio thread and the window. A surface is Beatlayer code written against one interface, the `ControlSurface` trait: it receives its input's messages, sends its output's, reads the set and what the engine is doing, runs the same registered commands a person and an agent run, and gets a regular tick. Surfaces written as extensions later implement the same interface.

A surface's controls follow the context instead of a fixed list, which the manual calls instant mappings. Its device controls follow the selected device, a bank of eight parameters at a time; a device can be locked to a surface from its title bar's context menu, and then keeps the surface's hands whatever is selected, with a hand icon in its title bar. By default, arming a MIDI track locks the surfaces to its instrument. A surface that plays the Session View has a session ring, a block of tracks and scenes its grid controls, drawn as a coloured border over the Session View; its mixer controls follow the ring's tracks. Beatlayer's own declarative templates describe a controller's controls and their roles in a small text file, so a controller without a native surface works without code.

## Rules

### The host and the Control Surfaces table (WP-7.5)

- **R1.** The Tempo & MIDI page (L-SET-014) holds, under its MIDI heading and before Takeover Mode and the MIDI ports table, the Control Surfaces table: six rows, numbered 1 to 6, each with a Control Surface chooser, an Input chooser, an Output chooser and a Dump button, left to right. The Control Surface chooser lists None, then Beatlayer's native surfaces by name in alphabetical order, then the controller templates (R43); the Input chooser lists None and every MIDI input port, the Output chooser None and every MIDI output port, by the names the MIDI system gives them. A new install has None in every row. (S2, S12)
- **R2.** The rows are kept in the preferences, not in the set, by the surface's ID and the ports' names, so they apply again after a restart and whatever set is open (Beatlayer's own). A row whose port isn't present keeps its name, shows it as missing, and its surface starts when a port of that name appears, as a track's input does ([MIDI I/O](midi-io.md) R8). (S2, S13)
- **R3.** A port a row names is open while the row names it, whatever its Track, Sync and Remote switches say, and a port serves one row at most: choosing a port another row uses is refused, naming that row (Beatlayer's own). Up to six surfaces run at once, several of the same kind among them, each on its own ports. (S2, S13)
- **R4.** A message on a surface's input goes first to the manual mappings, while the port's Remote switch is on and a mapping matches it ([remote mapping](remote-mapping.md)); one no mapping takes goes to the surface. A message the surface takes never reaches a track or a mapping. A surface may hand a note or controller message back to the tracks, which then receive it as from its input port when that port's Track switch is on, and the Control Bar's track input indicator lights for it ([MIDI I/O](midi-io.md) R25). (S1, S3, S4, S7)
- **R5.** A surface can play notes and controllers into the tracks as its own source: they reach every MIDI track whose input is All Ins or the surface's input port, on their channel, monitored and recorded as that port's messages are ([MIDI I/O](midi-io.md) R7 and R12), even when the port's Track switch is off (Beatlayer's own: how a controller's pads that arrive on its surface port play the selected instrument). (S3, S9, S13)
- **R6.** A surface is an implementation of the `ControlSurface` trait (Beatlayer's own interface). The host gives it, in order: each message from its input, whole (a system-exclusive message included), with the time it arrived; a tick 50 times a second (Beatlayer's own rate); and, on each tick, a read model: the document as the main thread last published it, the engine's published state (the slots' states and playing positions, the transport, the tempo, the tracks' meters), the selection, and the surface's own ring, banks and lock (R17 to R38). The surface answers with messages for its output, in order, and the commands it wants run. It reads nothing else and changes nothing except through those commands. (S13)
- **R7.** The host runs every surface on one thread of its own, never the audio thread or the main thread. A command a surface asks for is queued to the main thread and run there in order, by ID with JSON arguments, exactly as the same command from the window or an agent: the same checks, the same undo step and its name, the same refusal. A surface's commands are the person's own, so a gesture on it (a knob turned, a fader moved, a button held while others are pressed) is one undo step from its first change until the control is released or, for a control with no release, until it has rested 500 ms (Beatlayer's own), and agents' calls wait while it lasts ([agent permissions](agent-permissions.md) R5). (S13)
- **R8.** A surface's output is sent in the order the surface gave it, from the host thread straight to the port, at once; a surface that needs a message on a beat stamps it with the moment and the port's backend sends it then ([MIDI I/O](midi-io.md), scheduled output). A surface that sends faster than its port takes has its oldest unsent messages for the same control dropped first (Beatlayer's own). (S13)
- **R9.** A surface starts when its row has it and its input is present (and its output, for a surface that needs one): the host makes it, gives it its ports, and calls its start, where it sends the controller whatever puts it into the state the surface drives, and fills every light it owns. It stops when its row changes, its input goes away, the set closes or Beatlayer quits: its stop sends what gives the controller back its own state, with its lights put out. Opening another set restarts every surface's ring and banks (R30) and keeps the rows. (S2, S13)
- **R10.** A surface that panics, or doesn't return from a call within 100 ms (Beatlayer's own), is stopped; its row reads its error, the other surfaces keep running, and choosing the surface again in the row restarts it. (S13)
- **R11.** The Dump button is enabled while its row's surface declares a setup to send and its output is present. Pressing it, or `control_surface.dump` (`external`), sends the setup to the row's output, as the surface gives it, and changes nothing in the set. (S2)
- **R12.** What a surface holds (its ring, its banks, its mode, the device it follows, its locks) is surface state: never saved with the set, never an undo step, and gone when the surface stops (Beatlayer's own). (S6, S13)
- **R13.** `control_surface.list` (`read`) reports the six rows: each row's surface by ID and name, its input and output by name with whether each is present, whether the surface runs, is waiting for a port or stopped with an error, whether it can be dumped, and, for a running surface, its state: its ring (R28), the device it controls and whether that device is locked (R17, R23), its bank (R19) and its own mode by name. `control_surface.set` (`external`, as it opens and closes ports) sets a row's surface, input and output, any of them, and is read back by `control_surface.list`'s `rows`. `control_surface.surfaces` (`read`) lists every surface the chooser offers, native and template, with whether it can be locked to devices and the size of its ring. (S13)
- **R14.** Choosing a surface, a port or None in the table runs `control_surface.set`, and pressing Dump runs `control_surface.dump`, so the window, a surface and an agent reach the same commands. (S13)
- **R15.** A message a surface takes lights the Control Bar's remote input indicator, and a message it sends lights the remote output indicator, as a mapped message does ([remote mapping](remote-mapping.md) R41; L-CTRL-026). (S4, S12)
- **R16.** Nothing in the host runs on the audio thread, and nothing it does makes the audio thread wait: the engine's state reaches it through the snapshots the main thread already reads, and notes it plays into tracks (R5) cross on the MIDI input queue as any port's do ([MIDI I/O](midi-io.md) R14). A test surface, on test ports, drives every rule here headless. (S13)

### Instant mappings and device banks (WP-7.6)

- **R17.** A surface's device controls follow the device in focus: the selected track's selected device ([device chains](device-chains.md) R23), or, on a track with none selected, its first device; a track with no device gives them nothing. Selecting another device or track moves them at once. A surface that's locked (R23) or has its own device navigation (a controller's device buttons, run through `device.select`) is the exception. (S3)
- **R18.** A device's parameters are offered to a surface in banks of up to eight, each with a name. A surface shows one bank of the device at a time; moving to the next or previous bank stops at the first and last, and a device a surface comes back to shows the bank the surface last showed it while the surface runs (Beatlayer's own). (S3, S5)
- **R19.** Each native device type declares its banks with its parameters' descriptors (Beatlayer's own bank definitions): an ordered list of named banks, each naming up to eight of the type's parameters in the order its controls take them, the first bank holding the device's main controls. Every parameter that a person can automate is in at least one bank; one may be in several. A type that declares none has the generic banks: its parameters in descriptor order, eight at a time, named "1–8", "9–16" and so on. The parameters a device lists as menu options or as its title-bar switch come last, in a bank of their own. (S3, S13)
- **R20.** A rack's banks are its macros: macros 1 to 8, named "Macros 1–8", then, once more than eight show in its macro view, macros 9 to 16, named "Macros 9–16" ([macros](macros.md) R1 and R2). A macro is named after its parameter or "Macro N" there as it is in the rack ([macros](macros.md) R10). (S3, S13)
- **R21.** A plug-in device's banks are its configured list ([CLAP hosting](clap-hosting.md) R5), in its order, eight at a time, named by their positions ("1–8", "9–16"); a plug-in whose configured list is empty offers all its parameters the same way. A change to the list changes the banks at once, and a surface on a bank that no longer exists shows the last. (S13)
- **R22.** A surface's absolute control moving a bank's parameter sets it through the parameter's own command, taking its range as a mapping from the parameter's bottom to its top, and follows Takeover Mode ([remote mapping](remote-mapping.md) R28 and R29) whenever the parameter it reaches changes: after a bank, a device, a lock or the ring moves. A relative control steps the parameter as a relative mapping does. A parameter held by a macro ([macros](macros.md) R11) isn't moved, and the surface reads it as held. Instant mappings are never listed in the Mapping Browser and never saved. (S3, S5, S6)

### Lock to Control Surface (WP-7.6)

- **R23.** A device can be locked to a running surface that supports locking, through Lock to in the device's title bar menu ([device chains](device-chains.md) R41) or `control_surface.lock` (`read`: it changes surface state only, R12), naming the device and the row. While locked, that surface's device controls stay on the device whatever is selected; a surface locks to one device at a time, so locking another moves the lock; locking again, or `control_surface.unlock` (`read`), gives it back to the device in focus (R17). A device may be locked to several surfaces. (S3)
- **R24.** A locked device keeps its lock when it moves in its chain, to another track, into or out of a rack, or is renamed; when it's deleted, cut or its track is deleted, the lock ends and the surface follows the device in focus again. Undoing the deletion doesn't bring the lock back. (S3; Beatlayer's own)
- **R25.** A locked device's title bar shows the hand icon ([device chains](device-chains.md) R42) while any surface is locked to it, whether the lock came from the menu or from arming. (S3)
- **R26.** Arming a MIDI track ([mixer](mixer.md), `mixer.set_arm`) locks every running surface that supports locking, and isn't locked by hand, to the track's instrument: the first instrument or instrument rack at the top level of its chain, or nothing on a track without one. With several tracks armed, the most recently armed wins. Disarming the track, or deleting its instrument, ends a lock that arming made, and the surface goes back to the device in focus, or to the instrument of another armed track, the most recently armed. A lock made by hand isn't replaced by arming. (S3; the order among several armed tracks is Beatlayer's own)
- **R27.** A surface that doesn't support locking isn't offered in Lock to, and arming doesn't lock it. `control_surface.surfaces` says which surfaces support it (R13). (S3)

### The session ring and track banks (WP-7.6)

- **R28.** A surface that plays the Session View has a session ring: a block a fixed number of tracks wide and scenes tall (the surface's own size: eight by eight for an 8 × 8 grid), from a first track and a first scene. A surface without clip launching has a ring zero scenes tall, so its mixer controls still have tracks (R33). Its tracks are the Session View's columns in order: the audio, MIDI and group tracks, a folded group's tracks left out, then the return tracks; never the Main track. A ring starts at the first track and the first scene. (S10, S11)
- **R29.** A ring moves by `control_surface.move_ring` (`read`), naming the row and its new first track and first scene, or a step: one track left or right, one scene up or down, or a page, its own width or height. It stops where its last column holds the last track, and its last row the last scene; when there are fewer tracks or scenes than its size, it stays at the first. A surface's arrows run it, and a surface reads, through the read model, which way the ring can move. (S10, S11)
- **R30.** A ring keeps its first track and scene by ID while the set changes: inserting, deleting or moving tracks or scenes before it moves it with them; when its first track or scene is deleted, it takes the one now at that place, or the last; folding a group that holds its first track moves it to the group. A newly opened set puts every ring at the first track and scene. (S10; Beatlayer's own)
- **R31.** Moving a ring doesn't change the selection, launch nothing and add no undo step. The Session View scrolls the least it needs to bring the ring's first track and first scene into view when a surface moves it ([Session View](session-view.md) R37). (S10; Beatlayer's own)
- **R32.** A ring's slots are what the surface's grid shows and plays: a slot in the ring is reachable from the surface at its column and row, a column past the last track or a row past the last scene is empty, and a surface reads every slot's clip, colour and state for the ring from the read model. Each running surface's ring is drawn over the Session View ([Session View](session-view.md) R36). (S10, S11)
- **R33.** A surface's mixer controls (volume, pan, sends, mute, solo, arm, stop, select, crossfade assignment) cover its ring's tracks: its first channel strip is the ring's first track, and so on along the ring's width. A control past the last track does nothing and is dark. A send control reaches the send its surface has chosen, Send A first. (S11)
- **R34.** A surface's device controls (R17) and its mixer controls (R33) are independent: moving the ring doesn't move the device in focus, and selecting a track doesn't move the ring (Beatlayer's own). A surface that selects tracks does it with `session.select` or the track commands, as the window does. (S3, S10)

### Agents and readback (WP-7.6)

- **R35.** `control_surface.list` reports, for each running surface (R13): its ring's first track and scene by ID and index, its width and height, and which ways it can move; the device its device controls are on, by ID, with its bank's index and name, every bank's name, and whether that device is locked and how (by hand or by arming); and its own mode. `control_surface.lock`, `control_surface.unlock` and `control_surface.move_ring` are read back there. `device_view.state` reports each device's locks, naming the rows' surfaces (Beatlayer's own). (S13)
- **R36.** `control_surface.banks` (`read`) reports a device's banks by its ID, each with its name and its parameters by ID, name and value text, as a surface reads them, so agents see what a controller's knobs reach without one. (S13)
- **R37.** `control_surface.set_bank` (`read`) puts a running surface on a bank of the device its device controls reach, by index, as the surface's own bank buttons do, read back by `control_surface.list`. (S13)
- **R38.** Every instant-mapping rule holds headless: the test surface (R16) on test ports, driven by its messages, shows its ring, banks and locks through `control_surface.list` and the commands it ran through the undo history. (S13)

### Controller templates (WP-7.7)

- **R39.** A controller template is a text file in TOML (Beatlayer's own format), with the extension `.bltemplate.toml`, that describes a controller and gives each of its controls a role. It starts with `format = 1`; a file with a higher format is refused, naming the format it needs. Its `[surface]` table gives the template's name, its ring's width and height (R28; zero for a controller with no clip launching), whether it supports locking (R27), and optionally the port names it's for, as text a port's name contains. (S2, S3)
- **R40.** Each `[[control]]` in a template names one control: an ID of its own, the message it sends (a note or a controller number on a channel from 1 to 16, a pitch bend on a channel, or a 14-bit controller pair), its kind (a button that sends a value on press and another on release, a toggle, an absolute control, or a relative control of one of the four relative types, linear or accelerated, as [remote mapping](remote-mapping.md) names them), and its role. A role is one of: a slot of the ring at a column and row, a scene launch at a row, a track's stop, mute, solo, arm or select at a column, Stop All Clips, a track's volume, pan or send N at a column, the Main track's volume, a device control 1 to 8, next or previous bank, next or previous device, ring left, right, up or down, a page of the ring, play, stop, record, Session Record, loop, metronome, tap tempo, tempo, undo, redo, or Back to Arrangement. A control with no role isn't the template's and reaches manual mappings as any message does. (S3)
- **R41.** A button's control may carry feedback: the values its output sends for off and on, and optionally a value for flashing, on the same note or controller; an absolute control may carry feedback of its value, for a controller with motorised faders or rings. A template's `[[setup]]` lists system-exclusive or channel messages, as hexadecimal bytes, sent when the surface starts, and `[[goodbye]]` those sent when it stops (R9); `[[dump]]` those the Dump button sends (R11). (S2, S4)
- **R42.** A template surface runs on the host as a native surface does: its slot roles play the ring's slots as a mapped slot plays its slot ([remote mapping](remote-mapping.md)), its device roles follow R17 to R22, its absolute controls follow Takeover Mode, its mixer roles follow R33, and its feedback shows each control's state: a slot's button on while its clip plays and flashing while it's queued, where the template gives a flashing value. A role a template gives two controls runs from either. (S3, S5)
- **R43.** Templates come from two places: those bundled with Beatlayer, and the `Controller Templates` folder in the User Library (Beatlayer's own name), with its subfolders. The Control Surface chooser lists them after the native surfaces (R1), by their names in alphabetical order; a User Library template with the same name as a bundled one is listed instead of it. The folder is read when Beatlayer starts and whenever the Tempo & MIDI page opens. (S2)
- **R44.** A template that doesn't parse, or breaks a rule here (an unknown role, two controls with one message, a slot outside its ring, a setup that isn't whole system-exclusive or channel messages), isn't listed. `control_surface.templates` (`read`) reports every template file found, bundled and in the User Library, with its name, its path and, for a broken one, each error with its line. A row whose template is broken or gone keeps the template's name, as a missing port's row does (R2). (S13)
- **R45.** When a controller's ports appear and a template names them (R39), no row names those ports, and a row is free, nothing happens on its own: the chooser lists the template first among those for the ports, and the Settings read "Matches <template>" beside the ports in the MIDI ports table (Beatlayer's own). Only native surfaces that recognise their controller fill a row by themselves ([supported controllers](supported-controllers.md) R2). (S2)
- **R46.** Beatlayer bundles one template, Generic 8 + 8, for a controller with eight knobs as device controls, eight faders as track volumes, sixteen pads as a two-row ring of eight tracks, and transport buttons, on controller numbers of its own that a controller's editor can be set to (Beatlayer's own). Its file carries a comment for every key and role, so it serves as the format's example. (S2)
- **R47.** `control_surface.set` chooses a template as it chooses a native surface, by the ID `template:<name>`, and `control_surface.list` reports it so (R13). (S13)
- **R48.** Reading templates never runs code: a template is data, read on the main thread, and a surface made from one runs on the host thread as any surface does (R7). (S13)
