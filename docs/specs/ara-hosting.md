# ARA 2 hosting

- **Status:** implemented for VST3 (every rule has a test; the formats Audio Unit and CLAP are not hosted, see "Formats")
- **Work packages:** WP-5.41 (IMP-20, accepted on 24 October 2026). Beatlayer's own behaviour: Live 12 hosts no ARA plug-in, so nothing here is Live's to match.
- **Parity-matrix row:** none (an improvement over Live, [IMP-20](../05-improvements.md))
- **Checked against:** the ARA SDK 2.1.0's own headers and documentation (`ARAInterface.h`, `ARAVST3.h`), read on 24 October 2026; the manual has no ARA section

## The behaviour

A plug-in that implements Celemony's Audio Random Access (ARA 2), such as Melodyne or SpectraLayers, sees a clip's whole audio and where it sits in the song, not a live stream of it. Beatlayer hosts such a plug-in as a device on an audio track. The plug-in is then that track's player: it renders the track's clips itself, from the audio it read from the media store, and the track's clip player leaves those clips to it. The plug-in's own edits to a clip's audio live in its document, which the set keeps in its archive.

The host keeps one ARA document controller for each ARA plug-in the set uses. Every ARA plug-in is told what the set holds on the tracks it is on: the song's tempo and time signatures as its musical context, each of those tracks as a region sequence, each audio file the clips play as an audio source, each clip as an audio modification, and the playback regions that put them on the timeline. Whenever the set changes, including an undo or a redo, the document is brought up to date in one edit cycle on the main thread. A clip that leaves the set stays in the plug-in, deactivated, so undoing the deletion brings back the plug-in's edits with it.

This spec covers the host side of ARA for VST3 plug-ins. It leaves to [the VST3 hosting spec](vst3-hosting.md) everything a VST3 plug-in does as a device (its parameters, state, latency, and loan to offline renders), and to [the audio clips spec](audio-clips.md) and [the warping spec](warping.md) how the clip player plays what the plug-in doesn't take. A plug-in's own editor is the VST3 hosting spec's WP-2.10, which VST3 doesn't have yet: the plug-in's editor view is told what the Arrangement has selected, and shows it once an editor can open.

## Formats

- **VST3: built.** A class whose component answers ARA's `IPlugInEntryPoint` and `IPlugInEntryPoint2` is an ARA plug-in.
- **Audio Units: not built.** ARA binds an Audio Unit through properties of its `AudioComponentInstance`, and the SDK lists Audio Unit v3 (app extension) support as postponed; Beatlayer's Audio Unit host drives units through `AUAudioUnit` ([the Audio Unit hosting spec](au-hosting.md)), which gives no way to set that property. It waits for the SDK's v3 binding.
- **CLAP: not built.** CLAP's ARA extension is a draft that `clack-extensions` 0.2.0, the CLAP host's binding ([the CLAP hosting spec](clap-hosting.md)), does not bind.

## Rules

- **R1.** The host makes one ARA document controller for each ARA plug-in a set uses, from the plug-in's factory with the host's five interfaces, when the first instance of the plug-in is made; it starts ARA in the plug-in before, and shuts it down after, the controller. A controller is destroyed when no device or instance of its plug-in is left, and every controller goes with the set that made it, after the plug-ins bound to it. (S1) This is one controller for each plug-in, not one for the set: a factory makes controllers for its own plug-in only.
- **R2.** An instance of an ARA plug-in is bound to its plug-in's document controller with all three roles before it is first activated and before it is given its state, and stays inactive until its first sync has given it the regions of its track. After that the set's changes reach each controller as an edit cycle (`beginEditing`, the changes, `endEditing`, `notifyModelUpdates`) on the main thread, after every change to the set: a clip's move, trim, rename, length, and the undo and redo of each is an update of the objects the plug-in already has, never new objects. (S1, S2)
- **R3.** A track belongs to its first switched-on ARA device, and so to that device's plug-in, if it is an audio track that isn't frozen. A plug-in's document holds only the tracks it is the ARA device of. Its musical context carries the song's tempo as sync points (quarter 0, each tempo change, each quarter of a ramp, and one a quarter past the last) and its time signatures as bar signatures, and a change of either tells the plug-in the context's content changed. (S1)
- **R4.** The plug-in renders an unmuted audio clip that plays its file's range once, at 0 dB, with fades no longer than the 4 ms edge fades new clips get, and with no crossfade, transposition, detune, clip envelope or groove; and a warped clip only if the plug-in time-stretches. The track's clip player leaves exactly those clips out of its list, and plays every other clip of the track, and the Session clips launched on it, as before. The player has the clips back when the device is switched off or removed, and loses them when it is switched on or added. The plug-in's rendering replaces the track's signal, as an ARA playback renderer does. (S4, S6)
- **R5.** Each file the plug-in's clips play is one audio source, named by the file's content hash, with the file's own sample count, rate and channels; each clip is one audio modification of its file's source, named by its clip ID; each track is one region sequence. An unwarped clip is one playback region that plays the audio from its Start marker for the shorter of the clip's length and the span to its End marker, at the clip's place, all in seconds from the tempo map exactly, so the plug-in's rounding to frames agrees with the clip player's. A warped clip is one region for each stretch over which its warp map and the tempo map give a steady speed (a stretch for each warp marker, tempo change, and quarter note of a tempo ramp), each flagged as stretched. (S1, S4)
- **R6.** A modification whose clip leaves the set (deleted, moved to another track's plug-in, or made one the plug-in can't render) is deactivated for the undo history and kept, with the source it needs once nothing else does, up to 128 of them; when its clip returns by undo, the same modification is brought back and the plug-in has what it had. A source or modification whose file or clip is made again is a new object. (S1)
- **R7.** A plug-in's audio reader reads the whole decoded audio of the source's file from the media store, sample for sample, on the plug-in's own threads; a range outside the file reads silence. No reader is created for, or reads from, the audio thread: the host counts any read that comes from inside the plug-in's `process` call, and reports it in `ara.state` as `audio_thread_reads`, which is 0. The reader takes no lock, and a plug-in's render under the allocation trap and RealtimeSanitizer allocates, locks and blocks on nothing. (S1)
- **R8.** A playback region is added to or taken from a plug-in's renderers only while the plug-in is inactive. When a change needs that for a plug-in that is running, the host asks its node for the plug-in, which passes its input through until the plug-in is back; the host then edits the document, assigns the regions, and activates the plug-in again. A change that only updates regions (a move, a trim, a rename) does not take the plug-in away. A region is destroyed only after every renderer has let go of it. (S1, S5)
- **R9.** An offline render lends an ARA plug-in as it lends any VST3 plug-in, and the render's compiler leaves the plug-in's clips out of its clip players as the engine's does, so the render has them once, from the plug-in. (S5)
- **R10.** Saving the set takes each running controller's document archive into the set, with the plug-in's factory ID and its document archive ID, without an undo step; an archive for a plug-in that isn't running stays as it was. When a set opens, each controller is made with the archive the set holds for its plug-in, if the plug-in's archive ID or one it lists as compatible matches, and restores it in its first edit cycle, after the objects exist, so the plug-in's edits of each clip are back. Whether it did is in `ara.state`. (S1)
- **R11.** The plug-in's transport requests (start, stop, locate in seconds, the cycle range, the cycle switch) run as the transport commands a person's buttons run. (S1)
- **R12.** The plug-in's editor view is told which of its regions and sequences the Arrangement has selected, when the selection changes: the selected clips on its track, and the selected track. (S1, S2)
- **R13.** `ara.state` is the registered read command for ARA: each running plug-in's factory, devices and the tracks they render, the counts of sequences, sources and modifications, each playback region with its place in its file and on the timeline, the edit cycles it has been given, its audio readers' reads, the files it couldn't be given, and whether it restored its archive. `plugin.info` reports for an ARA device its factory, its track and how many regions its document holds. Clips are edited by their own commands, so ARA adds none that change the set. (S6)

## Tests

The tests run against two plug-ins. `bl-test-ara`, in `crates/test-ara`, is an ARA 2 VST3 plug-in built from source, so they run everywhere: it plays its renderer's regions from the audio it read (a stretched region by nearest sample), counts every use of ARA that breaks a rule above, keeps a count of the updates each modification got, writes the counts into its archive, and logs what its editor view was told. The ARA SDK's own example plug-in is built on the test machine and never committed: with Xcode on macOS, fetch the SDK and the VST3 SDK it needs (`cmake -P install_vst3sdk.cmake` in the SDK's root), configure `ARA_Examples` for Xcode with `-DARA_SETUP_DEBUGGING=OFF`, build the target `ARATestPlugInVST3` with `CODE_SIGN_IDENTITY=-`, and set `BL_ARA_TEST_PLUGIN` to the `.vst3` it makes; without the variable those tests say they were skipped. The SDK's example does not time-stretch, and keeps no report.
