# Agent perception: audio previews, analysis as text, and view captures

- **Status:** implemented (R1 to R9 each have a passing test; R8's capture of the live window was checked by hand)
- **Work packages:** WP-1.16, building on WP-1.15 (the agent API), WP-1.15b ([agent-permissions](agent-permissions.md)), and WP-1.12 ([export](export.md))
- **Parity-matrix row:** none: the agent API is Beatlayer's own (D17), and perception adds nothing a person sees
- **Checked against:** the architecture's "Agent control" (the Perception row), the export spec, ITU-R BS.1770-4, EBU R 128, EBU Tech 3341 and 3342, 11 October 2026

## The behaviour

An agent can't hear the speakers or see the screen, so three tools perceive for it. `preview` renders a short range of the set, the whole mix or one track, offline through the export's render, and hands it to the MCP client as a WAV file the model can listen to. `analyze` measures a preview, or a range it renders itself, and reports plain numbers with units: loudness and true peak as EBU R 128 reports them, sample peak and RMS, the level in each octave band, a tempo estimate, a key estimate, and the times of transients. `capture_view` returns one of the app's views as a PNG image, as the person sees it, for a model that reads images; only the running app can draw one, so headless it says it's unavailable.

All three only read. They change nothing in the set or on disk, never ask the person, show nothing on screen while they work, and never touch the audio thread: previews render on a copy of the set with an engine of their own, so playback on the device carries on undisturbed. This spec covers the three commands and tools, the formats they return, and the reference values the analysis is held to. It adds no menu item, key, or on-screen piece.

## Rules

- **R1.** `perception.preview`, `perception.analyze`, and `perception.capture_view` are registered commands with schemas and descriptions, in the read class, with no key or menu item. The agent API serves them as the tools `preview`, `analyze`, and `capture_view`, which never ask the person. (S1)
- **R2.** A preview's range is the export's: `start` and `length` if given, else the Arrangement's time selection, else the whole set, played straight through without the loop. It's cut to its first **30 seconds**, and the result says so (`truncated`, and `end` where it stopped). An analysis that renders its own range is cut at **ten minutes**. A preview is at the engine's rate unless `sample_rate` (8 to 192 kHz) is given, and 16-bit with triangular dither unless `bit_depth` says 24 or 32 (float). The last **4** previews are kept, by ID, as samples. (S1, S3)
- **R3.** `track` previews or analyses one track as it sounds soloed: the set rendered with that track soloed alone (through its groups and the Main track, with its sends' returns while Solo in Place is on), the set itself unchanged. The Main track is refused (leave `track` out for the whole mix), as is an unknown track; a track whose activator is off is noted as silent. (S1)
- **R4.** The `preview` tool returns the result as JSON and the WAV file as an `audio` content block (`audio/wav`), or, to a client that agreed protocol 2024-11-05, as an embedded resource with a base64 `blob`. Each kept preview is also a resource, `beatlayer://preview/<id>.wav`, in `resources/list`, read with `resources/read`, and named by a resource template. (S11)
- **R5.** The analysis reports, each rounded to a hundredth of its unit unless noted: integrated loudness, momentary and short-term maximum (LUFS), up to 60 short-term readings spread over the audio, loudness range (LU), and true peak (dBTP), per BS.1770-4 and EBU R 128; sample peak, RMS, and crest factor in dB, overall and per channel (a full-scale sine's RMS is −3.01 dBFS); the level of each octave band from 31.5 Hz to 16 kHz, cut at the Nyquist frequency, in dB as the RMS level reads; the tempo in BPM from 40 to 240 with a confidence from 0 to 1; the key, its correlation, and the runner-up; and the transients, up to 500, in seconds (to 0.1 ms) and as bar.beat.sixteenth under the set's tempo map when the preview was made. A measure with nothing to measure (silence, or audio too short for its window) is null. `measure` limits what's measured. (S4 to S10)
- **R6.** The analysis matches these reference values on fixtures generated in code, rendered through a preview of a set built through the agent API:

  | Fixture | Measure | Reference | Tolerance |
  |---|---|---|---|
  | Stereo 1 kHz sine at −23 dBFS, 20 s (EBU Tech 3341, signal 1) | Integrated and short-term maximum loudness | −23.0 LUFS | ± 0.1 LU (Tech 3341) |
  | The same | True peak | −23.0 dBTP | ± 0.2 dB (within Tech 3341's +0.2/−0.4) |
  | The same | Sample peak; RMS; the 1 kHz octave band | −23.00 dBFS; −26.01 dBFS; −26.01 dB | ± 0.05 dB; ± 0.05 dB; ± 0.1 dB, every other band at least 60 dB down |
  | Pink noise, −20 dBFS RMS, 10 s (equal power per octave from 20 Hz) | Each octave band | The RMS level less 10.1 dB | ± 1 dB (± 1.5 dB for 31.5 Hz) |
  | Click tracks at 120 and 97 BPM, the first click 0.25 s in, 12 s | Tempo | 120.0 and 97.0 BPM | ± 0.5 BPM |
  | The same | Every click's start | The time it was written at | ± 5 ms |
  | I–IV–V–I in C major; i–iv–V–i in A minor | Key | C major; A minor | Exact |

  The analysis code is also held, on signals it measures directly, to EBU Tech 3341's signals 1 to 5 (± 0.1 LU), Tech 3342's signal 1 (10 LU ± 1), BS.1770-4's K-weighting coefficients at 48 kHz (to 10⁻⁸), and sines whose samples miss their peaks (fs/4 at 0° and 45°, fs/6 at 60°, fs/8 at 67.5°, each with a true peak of −6 dBFS) to ± 0.05 dB. (S2, S4 to S10)
- **R7.** Previews and analyses render offline on a copy of the set with an engine of their own, through the export's render (`bl_shell::export::render`). They don't stop, pause, or disturb the engine playing the set on the device, and allocate nothing on its audio thread. In the app, a preview or a range analysis of a set without a CLAP device renders on the host's `bl-preview-worker` thread: the tool call defers, the window keeps drawing, and the reply comes when the render finishes; renders queue one at a time, and those still waiting or running when the window closes fail. Headless (`bl-cli mcp`), and for a set with a CLAP device (whose plug-ins are main-thread objects, offline plug-in renders R1 to R4), they render on the calling thread. (S1, S3; WP-2.28, [#1](https://github.com/loombridge/beatlayer/pull/1))
- **R8.** In the app, `capture_view` captures `window`, `arrangement`, `session`, `mixer`, `browser`, `detail` (the Clip or Device View with the Info View), or `settings` (the Settings window). A view not on screen fails at once, naming the command that shows it (`view.toggle_session_arrangement`, `view.toggle_browser`, `mixer_view.toggle`, `app.settings`); a minimised window fails too. Otherwise the call waits for the window's next frame, which the host draws a second time into an offscreen texture with the window's own renderer and reads back, so the image is exactly what the window drew whether or not the system presented it; the view is cut from it, scaled down to fit `max_size` pixels on its longer side (256 to 4,096, default 1,568) by averaging each output pixel's area, and encoded as PNG on a thread of its own. The tool returns the image as an `image` content block (`image/png`) with its size and pixels per point. A capture whose window draws nothing for 3 seconds fails. (S1, S11)
- **R9.** Headless (`bl-cli mcp`), or once the app's window has gone, `capture_view` fails with a message saying view captures need the app's window and that `preview` and `analyze` work here; captures waiting when the window goes fail. `perception.capture_view` run through `run` says only the `capture_view` tool returns the image. (S1)
